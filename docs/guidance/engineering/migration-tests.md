# Migration tests

A service's migration chain is proven at the lowest level that can show it, against
real database files and never a doubled connection:

- **The engine.** A migration engine's unit tests classify every result from tables
  and recorded ids and render each refusal; its library integration tests run it over
  real files — a fresh chain, a rerun, adoption without running the baselines, ahead
  and unsupported databases refused unchanged, a migration failing after DDL leaving
  no trace, a read-only check creating no file.
- **The floor fixture.** A service whose chain adopts a release's databases commits
  that release's schema as a fixture — its schema snapshot, its recorded migration
  ids, and its DDL — generated by running the release's published packages on a
  fresh database. A fixture is regenerated only to correct it against its release, or
  for a new floor.
- **The chain.** The baselines alone reproduce the fixture's snapshot exactly; a
  database built from the fixture's DDL with the floor's ids is adopted, applying
  exactly the later migrations and keeping its rows, and ends with the same snapshot
  and ledger as a fresh database; a rerun changes no byte; a database missing a floor
  id, or holding tables with no ledger, is refused unchanged; and each later
  migration's rewrite is proven. A test of a single later migration starts from a
  database built from the fixture, the real upgrade path.
- **The command and the startup check.** The migration command is driven through its
  entry point: its check mode exits unsuccessfully on a behind or missing database,
  listing what differs and changing nothing; the command refuses an ahead database;
  two configurations differing in anything but the database location and log level
  give one schema and one set of rows. The application's startup check refuses each
  state it must, naming the command.
- **Opening a store creates nothing.** A test starts the real application over a
  database its chain migrated, opens every store it composes, and asserts the schema
  is unchanged, so a table created when a store opens fails it.

A migration test with no application — a real component against real storage — is
library integration ([Test levels](test-levels.md)). A test that needs a migrated
database for another subject migrates it through the service's chain; a test that
builds its tables directly from the models instead proves nothing about the chain's
schema. A system test that starts every service on a fresh database shows each chain
builds a schema its service runs on; adoption of a release's databases is proven only
by the chain tests.
