# Storefront Publication Architecture

The [normative contract](spec.md) defines seller publication behavior. This document explains why storefront market state is separate from physical capacity authority.

## Seller-owned market state

A storefront is the seller's market-facing authority. It composes domain codecs, seller policy, publication, negotiation, settlement hooks, and operator-visible deal state. Registries hold discoverable copies; buyers hold received views; neither replaces storefront ownership of the listing and deal lifecycle.

The storefront may publish to multiple registries, but each publication remains derived from seller state and signed under the complete canonical publisher principal expected by that registry. The listing ID and storefront URL remain stable commercial subjects; changing an authorized credential does not manufacture a new listing or transfer ownership implicitly.

Seller-owned state is commercial, never physical. Hosts, resources, pool membership, and capacity are the site authority's, read through projections, and a storefront keeps no copy to fall back on. A VM storefront database written before that boundary may still hold the inventory tables it once kept. They are frozen, not dropped: a fresh database never creates them, and no storefront code, including a startup migration, reads or writes them, so their rows are history rather than state. They stay because an operator may need them to declare the same inventory at provisioning, reconciled first against what the site already holds; nothing copies them across, since a row recorded before the cutover is no evidence of what is available now.

## Immutable domain ownership and publication

The common storefront validates every explicitly configured contribution at
its application root and freezes each exact contract. Bare metal exports one
validated contract builder through `market.storefront_contributions`; its
standalone executable composes that same contribution with bare-metal seller
policy and provisioning adapters. A shared shell can therefore select it
without importing VM services or replacing domain-owned codecs and lifecycle
semantics.

Every derived listing persists one common binding containing trusted site,
offering mode, exact domain identity/version, public source envelope,
collision-safe pool or Physical Resource provenance, and the backing label its
pool declared. Every domain builds a listing's capacity binding,
`PublicationBinding(site_id, offering_mode, source_id, backing)`, from that
record through `publication_binding`, and never from a published payload;
`backing` is the delegate the recorded label selects, so two bindings differing
only in backing are unequal and no binding class names a category. Public
`offering_mode` is projected from this binding, not guessed from a
listing payload. One pool may therefore produce distinct VM and bare-metal
listings without creating competing domain-specific mapping authorities.
Negotiation and artifact bindings copy the frozen selection, and repository
rehydration resolves it only through the installed contribution registry;
neither a singleton, optional default, payload-shape guess, nor domain-name
branch may replace it.

Publication runners are built from the configured registry once. Disabling a
contribution removes its source and wait path; withdrawing a pool mode closes
new listings for only that mode. Accepted records retain their binding.
Mapped capacity traffic pins the selected site and never falls back to another
authority on refusal or outage.

## Advisory publication, authoritative admission

A listing is an offer based on the seller's latest complete capacity view. It is not a physical reservation.

```text
site projections → storefront cache → listing reconciliation → registry
       │
       └──────── authoritative reservation occurs at the site
```

Publication must be feasibility-based rather than derived solely from aggregate totals. An unavailable site is not authoritative evidence of zero capacity, so refresh failure retains the last complete cached generation and records staleness instead of closing listings destructively.

## Projection families

Individual-resource and grouped-capacity listings need different inputs:

- resource-pool projections expose allowlisted facts for resources the seller intentionally offers individually;
- capacity-bucket projections group identical available shapes into deterministic criteria and counts without exposing backing resource identities.

The families have independent revisions and digests. A storefront replaces each cached generation atomically, preventing readers from observing a partially refreshed projection. Grouped projection rows are publication hints, not allocation targets.

Every storefront that derives listings from site projections holds both families for every configured site, in one per-process state the capacity-publication kit owns (see the [market composition architecture](../market-composition/architecture.md#storefront-composition-kit)). Publication, every listing-source check, override status, and system status read that state; none fetches a site per listing type. Holding both families everywhere, rather than the families each composition happens to read, is the one shape to refactor from as the compute storefronts converge on one storefront that pulls every resource pool once for all listing types. The state holds whatever generation a site serves; a domain's acceptance rule for a generation applies when that domain reads it, so one domain refusing a generation holds only that domain's listings at the site.

Bare-metal publication derives from the resource-pool projection alone, one candidate per Physical Resource carrying a `bare_metal.v2` publication view. The view is the one the site builds from the capacity declaration admission accounts against, so it cannot name a different machine than admission does; a storefront building its own view from a publication attribute could. The shared declaration reader judges one site generation as a whole, so a resource's pool, that pool's declarations, and the resource's view all come from one document. The site builds the view's availability from the same ledger rows when it serves the projection, so the held generation carries the machine's availability as of its poll, and bare metal derives nothing from the capacity-bucket family it also holds.

Within that document a resource's pool is the pool entry that contains it. The view repeats the pool identifier so it is self-contained, and pool membership decides whether a resource may be published, so the two copies may not disagree: a view naming another pool refuses the whole site generation, as a view naming another Physical Resource does, and the site is held rather than read either way.

Bare-metal publication reads each configured site's held view of the resource-pool family — value and identity together, for every site before anything is awaited — because each candidate carries the generation's revision and digest. A site whose state holds no value is unknown, not empty. A stale generation, one whose latest poll failed, is still derived from, since holding a site's listings through an outage is publication's job. Publication and the opening recheck each run the domain's acceptance of the generation (`trusted_bare_metal_projection`) on the held value they read; a refused generation holds the site's listings as `site_projection_refused` and makes an opening retryable. A domain hook on the shared state was rejected, because it would freeze every listing type at that site on one domain's rule.

## Reconciliation

Reconciliation compares desired publication with current seller state and registry state. Capacity events trigger reconciliation regardless of which seller action caused the availability change, because a shared site may serve several storefronts. Deal-scoped outcomes travel through a separate owner-specific route and are not broadcast as capacity deltas.

Two reconciliations run over listings, and they differ in scope:

- **Source publication** applies to every listing, backed or not. A removed or disabled source closes the listings derived from it, and a changed source is reflected according to the identity rule below. Without it an unbacked listing's advertisement would outlive its declaration indefinitely, which is worse than a stale capacity number because no later event corrects it.
- **Capacity availability** applies only to listings whose backing availability bounds, with its close-before-reopen sequencing. An unbacked listing has no availability to track; its quantity is bounded by what its source declares, which is what being inexhaustible means. The binding's backing delegate decides the scope, in the form each domain selects listings in. Where listings are selected in a query, as VM's availability paths — capacity events, a released reservation, a failed deal — select them, the query binds the registry's `labels_reconciled_by_availability()`, so an unbacked listing never enters them. Where listings are judged one by one, as bare metal's publication pass and API credits' reconciliation judge them, availability reaches a listing only through the delegate's `judge`, which never asks it of supply availability does not bound.

Bare-metal publication keeps the two apart by classifying every resource into exactly one class and building its closes from those disjoint classes: a *candidate* (pool admits bare metal, declaration enabled, and, where its pool's backing says availability bounds it, the machine wholly available) is published, refreshed, or reopened; an *unavailable* resource (as a candidate, but a backed machine that is leased) closes its listing for availability and reopens it when free; a resource in a pool whose declarations do not resolve, whose declaration does not read as a shape, or for which the site could build no view is *held*; and anything else — a disabled declaration, or a pool that does not admit bare metal — is *withdrawn* and closes as a source withdrawal, as does a listing whose resource is no longer projected under the pool its binding records. Whether availability is asked at all is the delegate's: classification goes through its `judge`, which never asks it of an unbacked resource. Enablement is read from the projected resource, never from the view, because the site builds the view's `available` from the declaration's enablement and whole-resource availability together; reading it would turn a withdrawn declaration into an availability close. A resource the site built no view for is held rather than closed because its declaration is unreadable, not withdrawn: closing it would turn every declaration fault into a delisting. Disjointness is also mechanical: the kit runtime refuses a close plan naming one listing twice.

The opening recheck reads the projection the storefront holds for the listing's site and goes through the binding's delegate, so an unbacked listing is refused only by its declaration — its shape, its region, its Physical Resource, or its resource now projected under another pool, which the recheck finds by the bound pool and Physical Resource and answers as no longer projected under its pool. A held resource the site built no view for is refused as a declared mismatch naming the site's problem: the declaration no longer yields the listing it published, so an opening against it cannot succeed on retry, while publication holds the listing so that the fault never delists it. A site whose projection the storefront does not hold, or holds unconfirmed, refuses openings as retryable for either backing.

A candidate whose payload would carry no settlement option and no accepted escrow yields no listing, in VM and bare metal alike. Settlement admissibility does not cover that case on its own: it refuses only when it drops an option, and a contact-only candidate whose origin has no configured contact dropped nothing. Whether the candidate's open listing closes or is held is decided by classifying each mechanism of its admissible clauses — its pool's override, or the configured clauses where it has none, after admissibility for its backing; a mechanism outside them could never settle this listing, so its readiness says nothing about the offer it published. When every such mechanism is ruled out by the storefront's configuration, or no clause resolves, the storefront can no longer say what its policy would sell, and the listing closes through reconciliation as `no_settlement_option`, reopening under the same identity on the first cycle whose payload builds again. When any is unknown, because its chain or service could not be reached, the listing is held at its last terms and negotiates normally, as a site whose projection is not held is unknown rather than empty; settlement fails retryably where it touches the unreachable dependency. A mechanism ruled out beside an unknown one does not change that, since the offer published is still one the storefront would make once the dependency answers. Closing whenever any mechanism is ruled out would let an unrelated, unusable mechanism decide whether an outage delists supply; classifying every configured mechanism would let an outage on one the candidate could never use hold a listing whose close is due. The core publication runner is schema-opaque, so each publication source supplies a `close_candidate_listing` hook, and `kit/capacity-publication`'s `RefusedCandidates` is that hook for every storefront driving its cycle through the kit: it records the refusal under the candidate's site and closes the open listing bound under the candidate's derivation key through the domain's own reconciliation close. Any other payload failure is reported as `payload_unbuildable` and leaves the listing as it is, so a defect never delists anything.

Two comparisons gate a refresh and every reopen, and backing is compared first. `backing_changed(binding, source_backing)` in `kit/capacity-publication` asks whether the delegate a listing's binding records differs from the one its source's pool now declares; every domain applies it on every refresh, every reopen, and every source check. A mismatch closes an open listing, is reopened or refreshed in place by no path, and is a declared mismatch to the seller's inventory guard, so supply that moves between backed and unbacked is a new listing with its own binding. Backing is neither an identity field nor a term of sale, because a pool re-created under the same identifier with the opposite backing yields a candidate under the same derivation identity, which would otherwise refresh in place. Then a listing whose published identity differs from what its source now derives is not refreshed in place and is not reopened by any path, including one a capacity event drives. The publication runtime's refusal of a supplied binding that differs from the persisted one remains a backstop that raises a fault; the comparison runs first so a backing change is an ordinary close. The same derivation serves the seller's inventory guard, which compares a listing against a fresh derivation of its own source rather than against any matching row, because a field's provenance is decided per listing, not per field.

## Listing identity

A listing's identity is the physical resource it offers: the supply it draws from (site, and pool or Physical Resource), what the resource is (offering mode, resource type and subtype, and categorical attributes such as `gpu_model`), where it is (`region`), and how much one listing offers (the enumerated slice quantity and every other declared dimension it publishes). Everything else — price and pricing hints, settlement options, maximum duration, SLA — is a term of sale.

The line falls there for three reasons. A listing ID is what a buyer saves and negotiates against, and what accepted terms and settlement records reference, so changing what is sold under one ID reinterprets every such reference. Terms of sale are meant to move: a price change that orphaned buyer references would make every repricing a delisting. And the identity fields are the ones admission matches — the capacity claim carries the pool or resource, region, model, and requested dimensions — so what a listing is and what a reservation will look for are one set of fields.

A term change therefore refreshes an open listing in place, and an identity change closes it and, where the source still supports one, publishes a listing under a new derivation identity. A listing commits only to the fields it publishes: reconciliation never adds an identity field a listing did not publish, since that would make a new commitment under an existing identity. Capacity backing sits outside the split. It is not a property of the resource but of whether an admission authority stands behind the listing, and it is fixed on the binding when the listing is created.

A listing is tracked by one key: its common binding's derivation key. For a bare-metal listing that key is built from its site, offering mode, domain binding, pool, and Physical Resource, so a Physical Resource moved to another pool derives a new listing under the new pool's binding and its old listing closes as a withdrawn source. A second, domain-owned key that omitted the pool would find the moved resource's listing and refresh it in place while its binding still recorded the old pool, leaving advertisement authorized by a pool the resource no longer belongs to. A bare-metal binding's source, as the capacity-publication kit sees it, is its Physical Resource: the listing sells that one machine, whereas a fungible VM listing draws from its pool.

## Listing shapes and the storefront's authority

Every VM listing is a listing shape: a family-grouped statement of what one listing offers, in the compute family's vocabulary. API-credit publication does not use listing shapes; the family-grouped shape utility and the storefront pool-override kit are market-neutral, so another market can adopt the model. For a VM listing, a published dimension is a commitment, not a description. The capacity claim a VM listing produces requests every quantity the listing publishes, the site reserves each one, and fulfillment builds the resource from what was reserved. Publishing a member's whole memory on a one-GPU slice would therefore reserve and provision all of it for one GPU. So a VM listing publishes exactly the quantities its shape declares and nothing else. A dimension its shape omits is outside the listing's and the reservation's commitment: fulfillment may supply it from the pool's configured VM defaults, where they are set, or leave it to downstream provisioning, and keeping enough capacity for the dimensions a pool's shapes omit is the operator's responsibility.

The same rule holds for GPUs. A shape that states no `gpu` family commits no GPU, so its listing resource carries no `gpu_count` or `gpu_model` key at all, rather than a `null` one: a `null` would state a value the shape does not, and the registry's listing schema types a present `gpu_model` as a string. A stored listing whose resource holds a `null` GPU field and a fresh one omitting it compare as unchanged, so no stored listing churns. Whether a resource payload is compute is decided by one rule at every seam that decides it — the listing model's parser, the adapter registry publication calls, the compute test the claim builder and opening apply, and the buyer's display: an explicit `resource_type` selects its kind, otherwise a payload with a `token` key is a token resource and any other mapping is compute. Recognising compute by a `gpu_model` key, as a GPU-only vocabulary could, would turn a GPU-less listing into something no seam can parse, and dispatching on `region` would couple parsing to a field derived from a pool hint. A compute mapping that states no quantity is then refused by the shape kit's refusal of an empty shape, not by a separate check.

Shapes are stated or generated, never inferred. A pool's VM shapes come from exactly one source, in order: the storefront's own override for that site and pool, the pool's `listing_shapes` hint for the offering mode, and otherwise the VM domain's default generator. A stated list replaces the lower sources whole. The VM default generator yields, per GPU model among a pool's members, one GPU-only shape per count up to the largest declared that the storefront's configured admissibility default admits; the generator is the domain's seam for other default policies. How many of a shape fit is derived from the site's declarations, never declared or published.

The default stays GPU-only, so a member declaring no GPUs yields no default shape, and a seller sells VMs without GPUs by stating shapes on the pool hint or an override. A CPU slice has no natural unit to enumerate: one listing per vCPU count would publish on the order of two hundred listings for a large host and leave the memory each slice is given unreserved, one whole-member shape per member would sell a machine as one VM, which a VM seller rarely wants, and a ratio ladder would commit to a ratio nobody stated. A pool may therefore publish nothing (see [holding or closing a listing the storefront cannot fully derive](../../../docs/development/ARCHITECTURE.md#holding-or-closing-a-listing-the-storefront-cannot-fully-derive)), and the storefront reports it once, by site and pool, as `listing_shapes_required`, when it states no shapes, has an enabled member, and no enabled member declares a positive GPU count. A member is never reported on its own account, so a member without GPUs beside a GPU member is silent, and a pool with no enabled member is not reported, since stating shapes would not change what it publishes.

A shape is published only where some source member is resource-feasible for its claim, judged by the site's own predicate against declared capacity, and, for a capacity-backed listing, against current availability. Feasibility is not admission. It does not see the pool provider's host requirement, holds over a lease window, or physical-host conflicts, and the projection deliberately withholds the state that would let it; the site's reservation remains the admission boundary. A stated shape no member is feasible for yields no listing and is reported; it is never shrunk or replaced by another source's shapes.

A member's GPU count is no precondition for membership: a member declaring none, or zero, uses no GPUs, and feasibility judges each shape on the dimensions it declares, so GPU bookkeeping applies only to shapes that name GPUs. Only a malformed count still holds the pool. Making membership depend on the shape source instead, dropping GPU-less members unless a pool states shapes, would give one member two meanings. Every VM declaration and claim names the resource type `compute.gpu`, and admission treats a dimension a claim does not request as not requested, so a stated shape without GPUs lands on any member with the vCPUs and memory free, a GPU host included: a GPU machine's spare server resources may sell as VMs. The mechanisms are neutral and nothing forbids it. A distinct `compute.cpu` type chosen from the shape would forbid it, since a claim names one type and a host carries one declaration. The cost is the operator's to weigh: a CPU-only shape in a pool of GPU hosts can consume the vCPUs and memory a GPU listing would need, as any omitted dimension can.

How much one VM listing offers is its listing shape, and its derivation identity includes the shape's digest, taken over the family-grouped form so that renaming a flat field changes no key. Identity then depends only on what is offered: a site that later states the shape its pool was publishing by default keeps that listing.

### Bare-metal listing shapes

A bare-metal seller sells one whole machine, so there is no shape to choose. A bare-metal listing's shape is its Physical Resource's declaration read through the compute-family schema: the declared capacity dimensions other than `units`, and the declared attributes the schema names. Publication-only data a site copies into the bare-metal view is not a source. It is unchecked, and a shape built from it would describe hardware no admission ever matched. So an operator declares hardware where the site can see it, and a declaration that does not read as a shape holds only its own listing, reported by name. A machine without GPUs omits both GPU fields, and its shape states its vCPUs, memory, and storage alone; its listing publishes no GPU key. A declaration of `units: 1` alone states no shape, and `gpu_count: 0` is a non-positive quantity the vocabulary cannot carry, so both stay unresolvable rather than read as "no GPUs": substituting a meaning for a declared value would let a typo publish a machine.

The two domains share one schema, so a whole machine and a VM slice with the same hardware publish the same flat fields, and one filter finds both. Region comes from the pool's hint, as for VM. The compute registry requires one, so in either domain a pool without it is held rather than published with a guess: a missing region is a declaration to repair, not a withdrawn source, so the listings it already published stay open. For VM the hold is publication's alone; availability reconciliation, which region does not bear on, still closes a sold-out listing.

The commitment differs from VM's, and deliberately. A whole machine is held by exclusive allocation of one unit: the claim reserves exactly one `units` and requires the shape's attributes, so admission refuses a declaration whose model changed, while the quantities describe what that unit contains. Only the attributes the listing states are claimed, so a machine without GPUs claims none, and its claim still selects its Physical Resource and one `units`. An empty set of claimed attributes is therefore a valid record; a trusted record carrying none at all is broken and refuses the claim. Reserving each quantity separately would add nothing, since exclusivity already holds them all, and would let a partial declaration look like a partial machine. That is the commitment of a backed listing. An unbacked listing makes none: no admission authority stands behind it, so it constructs no claim and is never reserved, held, scheduled, or fulfilled.

Bare-metal supply may be unbacked. Every enabled pool advertising `bare_metal` yields candidates whatever its backing, and nothing in bare metal branches on the backing label: what differs between backed and unbacked supply is the pool's backing delegate's to decide (see "Reconciliation" and the [resource-pool management architecture](../resource-pool-management/architecture.md#advertisement-delivery-and-backing)). An unbacked listing's derivation identity is the one a backed listing has, its site and Physical Resource, with no host fields, because nothing delivers a host for unbacked supply. The site emits a resource's `bare_metal.v2` view whenever its declaration enables bare-metal publication, in an unbacked pool host or no host, so both backings are read through the one view; deriving an unbacked candidate from the capacity declaration instead would give the storefront a second way to read unbacked resources around the view. The declaration's `bare_metal_publication` attribute stays the opt-in for both. An unbacked resource is never judged against availability: an enabled, shaped resource is a candidate and a disabled one is withdrawn. Region, asking-rate, override, and shape rules apply to it unchanged.

Some of a listing's fields commit the marketplace to delivering something, and on an unbacked listing nothing would stand behind them. These are delivery terms — for bare metal `host_id`, `physical_host_id`, `access_methods`, and, on the view, `available` — and whether a listing carries them is its backing delegate's decision: the site's view builder passes them through the delegate's `carry_delivery_terms`, and the models validate them with its `delivery_term_constraints`. A backed listing carries every term, `access_methods` non-empty as declared; an unbacked listing carries none, even where its declaration names a host, since a declared host or access method on it would read as a machine and access the marketplace delivers. No default fills an absent term, because a default would publish a commitment nothing stands behind. The buyer-visible indicator is the published `capacity_backing`, which the compute registry schema filters exactly, so a buyer can ask for unbacked supply.

The view on the wire carries no backing label. Backing has one source, the containing pool entry, as pool membership does, so a backed view is unchanged and no second copy of backing can disagree with the pool's. The view's own model, `BareMetalResourceProjection`, checks only the structure of its delivery terms; the rule lives one level up, in `TrustedBareMetalResource`, the carrier the site's view builder and the storefront share. Its caller supplies the containing pool's label — `trusted_bare_metal_projection` takes the generation's resolved backing per pool — and its validator applies that label's delegate's constraints, so a backed view missing a term and an unbacked view carrying one are malformed views and refuse the site's whole generation as `site_projection_refused`, as a view naming another pool does. Resolving a generation's declarations is the reader's job and checking a view against a backing is the carrier's, so `arkhai_bare_metal` gains no dependency on the pool authority. The right label depends on the whole generation — one in which no pool carries either declaration comes from an older producer — so the storefront reads a generation's pools before its views, in publication and in the listing-source check, and passes `SitePoolReading.backings`; a pool whose declarations do not resolve has no label, no term check runs, and its resources are held. The site passes its own pool context's backing and builds its view through the same carrier after `carry_delivery_terms`, so a correct site cannot emit an inconsistent view; only a site of another build or a misbehaving one can.

The shape's digest completes the listing's derivation identity, with the Physical Resource still anchoring it: one resource derives one listing at a time. Without the digest, correcting a declared dimension would change an identity field the key does not capture, so the listing would close and never reopen. With it, the correction is a new key: the old listing closes as a withdrawn source and a successor publishes. That also upgrades listings bound before shapes existed, since their keys match no candidate.

Seller policy rechecks the source before agreeing terms. The bare-metal opening guard is a pure domain function that runs publication's own classification over the projection the storefront holds for the listing's site and compares the bound resource's shape digest and region with what the listing published. Publication and the guard therefore read a declaration through one code path, and from one held generation. The storefront only reads the held view and maps the outcome to a refusal; it calls no site, so an opening does not depend on its site being reachable, and a generation that is not freshly confirmed refuses as retryable (see "Projection families" and the seller's inventory guard in the [specification](spec.md)).

The recheck authorizes the opening against the listing as it then stood, and the storefront records that listing record with the negotiation. Every later round — continuation, acceptance, and force-accept alike — resolves against the recorded record, carrying the listing's current status, because the runtime builds acceptance from the record it resolved: a listing refreshed in place since the opening cannot change the escrow the buyer funds. A thread with no recorded opening record continues against the current one.

### Asking rates

A compute listing may publish the rate its seller asks for the listing's whole shape: `asking_rate`, an exact decimal-text amount, the opaque asset it is quoted in, and the period it is quoted per. It is a listing attribute, not a settlement option rate. A mechanism's rate governs what the runtime constructs and what an accepted obligation implies; the asking rate governs nothing, so nothing is derived from it and it is never derived from a mechanism rate. The two need not agree. Making the settlement carrier filterable instead would have left exactly the supply this serves unfilterable: deals arranged out of band settle by introduction, whose options are rateless by design.

The rate prices one listing shape, not a pool and not a dimension. A pool selling a one-GPU and an eight-GPU shape publishes two listings, and a pool-wide rate would misprice all but one. Pricing a shape a buyer proposes during negotiation is a separate concern; a published listing's shape does not vary, so one number per shape is what a catalogue needs. A buyer comparing listings that bundle different memory is therefore comparing bundled prices.

A site states rates in an `asking_rates` pool declaration, keyed by offering mode, each entry naming the shape it prices. Entries sit beside the shape rather than inside it, because a shape's digest is part of its listing's identity: a rate inside the shape would turn every price change into a close and a republish, where a rate is a term of sale that refreshes in place. A list of entries keyed by shape, rather than a rate wrapped around each stated shape, serves stated, generated, and derived shapes alike, which matters because a bare-metal pool states no shapes at all.

Resolution is the storefront's override for the site and pool, then the pool's declaration, then no rate. There is no configuration default: a storefront publishing for several seller sites would otherwise advertise its own blanket price as each site's. Every published rate is the origin pool's own statement or an explicit, per-site override. An override replaces the pool's list whole, and an empty list withholds every rate, since withholding a price is a commercial choice and, unlike an empty shape list, stops nothing.

A declaration or override the reading domain cannot read holds the pool's listings. That diverges on purpose from the pricing hints, which treat a malformed field as absent: dropping a public price the seller believes they published is worse than holding until it is fixed. A stated `null` is malformed for the same reason, not absent; the reader tests whether a key is present, because it exists for data the write path did not produce. The kit checks structure at every pool write, and the domain checks what only it knows: shape vocabulary, duplicate shapes, and accepted periods.

The accepted periods are this kit's own contract, `hour` today, held equal to the time units settlement arithmetic scales by through a test rather than imported from them. Widening it is a decision about what buyers compare, not a side effect of adding a settlement unit.

One resolver, in `kit/resource-pools`, serves both compute domains, generic over each domain's shape digest and vocabulary, because bare metal cannot import VM and the rule must have one implementation. It states the storefront's precedence beside the pool declaration's parser. Precedence is storefront authority, so splitting the two would draw that boundary more cleanly; it is not split because either destination costs more. `kit/pool-overrides` would need the resource-pool kit to parse the pool tier, and each domain would carry a copy of one rule. The override reaches the resolver as plain data, so no dependency points upward. The revisit trigger is a second consumer of pool-declared rates that is not a storefront.

A site cannot yet bound what a storefront publishing on its behalf may advertise or agree. Nothing commercial crosses the provisioning boundary today, mechanisms have no reverse conversion from base units to a decimal bound, and none of it applies to unbacked listings, which are never provisioned. Each entry already pairs a shape with its rate, so seller-side bounds could be added later as further fields of an entry without restructuring the declaration, when a seller site first needs that control. Nothing keeps a published rate honest either; the intended control is registry curation, outside the registry service.

### Shape pricing

A seller states a rate per capacity family — per GPU of a model, per vCPU, per GiB of memory or storage — in an asset, and a listing's settlement rate for that asset is its shape priced at those rates. The rate lives under the family it prices, in the same family-grouped nesting as the shape, not in a parallel map keyed by the same families: a second structure would make every read join two shapes and let them disagree. Which families are priced, and by what key, is the domain's explicit pricing projection rather than an inference from schema attributes, because which attribute a price varies by is a commercial choice and a schema may carry several.

A clause's stated rate is a flat rate for the whole listing and is never reinterpreted as a per-family rate. Reading an existing rate as a per-GPU rate would have multiplied the price of every listing above one GPU; keeping the two modes distinct means a configuration that states no family rates publishes exactly what it always did. Shape pricing starts where a seller states a family rate, and no family is special: a GPU-only pricing rule would bake today's mandatory GPU into the price model.

A family without a rate is not charged. Committing 64 GiB of memory does not mean charging for memory, and refusing the listing until every named dimension is priced would refuse every listing whose seller prices only its GPUs. What is refused is a listing whose rate would be zero in an asset, most often a mistyped asset; it is never published, so never negotiated. An unrated family is reported, so bundling is visible rather than silent.

VM terms and family rates are grouped by GPU model, and a shape stating no GPUs has none. It takes only the terms keyed by no model — the override's and the configured flat default's clauses — and the rates of the families keyed by no model: cpu, memory, and storage. A pool whose only clauses and rates are per GPU model therefore leaves such a shape no settlement option, and the shape is refused and reported as `no_settlement_option` while the pool's GPU shapes publish. Lending it a GPU model's terms would price a listing at rates its seller stated for hardware it does not offer.

A rate that cannot be read holds the pool, as an unreadable asking rate does, and for a stronger reason: falling through would publish a lower tier's rate, a price nobody stated for that pool, where an asking rate's fall-through publishes no rate. The provisioning service checks rate-list structure at every pool write, knowing no family name, and the storefront checks what only the domain knows. The storefront's own configured rates are the operator's input, so an unreadable one stops startup rather than holding pools.

Evaluation is an interface, not a formula: real capacity is not linearly priced, and the last GPU on a host is worth more than the first. Linear summation ships as the only aggregator; no caller reconstructs a total by multiplying a rate by its quantity, so a different aggregator changes every price without touching negotiation, publication, or settlement. It lives in its own foundation kit, `kit/capability-pricing`, rather than in `kit/capability-shape`, because shape is capacity vocabulary and pricing is commercial evaluation over it; `kit/settlement-runtime` knows no shapes, `kit/resource-pools` is an authority kit that buyers and hold billing should not depend on, and `kit/policy` is schema-free negotiation middleware.

The per-family quantity is not carried in the published rate. `RateValue` is on the wire, in option identity, and in escrow obligation data, so widening it would reach every mechanism, while the quantity is already in the shape being priced. The published option still carries one rate for the whole listing, and its identity still covers that rate, so a family-rate change that changes a composed rate changes the option's identity while the listing's identity, a term-of-sale question, does not change.

Every resolved family's rates are recorded on the storefront's listing record, including families the listing's own shape omits, so a revised shape a buyer proposes can be priced from the record. The record is a term of sale held on the generic listings table, opaque to core as `listing_resource` is. It is not published: the registry keeps a fixed set of listing carriers and would discard a new top-level field, and `listing_resource` is the capacity description, not a place for asset-denominated payment pricing. The registry receives each option's composed rate, which is what discovery compares. Every amount on this path is exact: rates are parsed digit by digit and summed as integers, never through a binary float or a fixed-precision decimal context, because base-unit amounts routinely exceed 64 bits.

### Shape constraints

A stated listing shape may bound what an agreed shape may state for each quantity, inline as `{offer, min, max}` (see the [admissibility model](../market-composition/architecture.md#capability-shape-admissibility)). Admissibility is the storefront's own policy. It is final because the storefront controls agreement: nothing else can make it agree to a shape. A constraint a site states on its pool's listing shape is therefore an input to that policy, advisory exactly as pool pricing is, and a limit that must bind every storefront acting for a site would be a site-admission constraint over claim dimensions instead. Admissibility never overrides what the site enforces, and admitting a shape says nothing about whether the site will serve it.

A listing's policy resolves from two tiers: the constraints its stated shape carries, from whichever source stated it, and the storefront's configured default, `[admissibility.defaults.vm]`. They merge per bound — the higher tier stating a field's `min` or `max` wins and an unstated one keeps the default's — so a site may replace a default value, even widening it, but never remove it by omission. Intersection was rejected because it would make the advisory hint only ever narrow the storefront's policy, and whole-declaration replacement because it would drop every default value a listing does not restate. An override's shapes replace the hint's list whole and do not inherit its constraints: an override cannot yet name the hint listing it would adjust, so each of its shapes is a listing of its own. A generated shape is nobody's statement, so its policy is the configured default alone, and the generator asks the kit which counts that default admits rather than generating and filtering.

A listing's identity is its base shape, the stated shape with each constrained field reduced to its offer. Changing a range does not change which listing it is; reconciliation re-evaluates it and closes it once its offer is no longer admissible. Asking rates match the base shape for the same reason.

**Why an uncomputable policy closes where pricing holds.** A storefront that cannot fully derive a listing either holds it at its last-published terms or closes it, and the [repository-wide test](../../../docs/development/ARCHITECTURE.md#holding-or-closing-a-listing-the-storefront-cannot-fully-derive) decides which. An unreadable rate holds, because the last price was the storefront's own offer. An unreadable shape list holds — base shapes are read before constraints, so a constraint that removes a required field makes the list unreadable — because an unreadable declaration is not a withdrawn one, and closing would turn every malformed shape into a delisting. When every base shape reads but a listing's policy cannot be computed — its constraints cannot be read, its tiers merge to an empty range, or its base shape is stated twice with different constraints — the storefront can no longer say what its own policy would sell. Keeping the listing open would advertise what that policy may exclude, and a site cannot be refused a projection, so closing that one listing is the signal that reaches the site's administrator. Closing the whole pool would punish listings whose policy is computable. For a conflicting duplicate, keeping the first entry would be order-dependent and silent, and intersecting the two would combine statements of which the author meant one; identical entries are not a conflict and collapse. A stated offer outside its own resolved range is not published either. Closing on an unusable constraint can churn a listing, which is accepted: it republishes as a successor once usable.

Pool and override writes catch what they can before publication. A pool write refuses malformed constraint structure and a base shape stated twice with different constraints, because a list that contradicts itself is a fault in the site's document whichever storefront reads it, and detecting it needs no domain vocabulary; whether a constrained path is a quantity is the domain's to judge, and a pool's shapes are never judged against a storefront's configured default. An override write is the storefront's own statement, so the VM contribution also refuses an unreadable base shape or constraint, an empty range against the configured default, and an inadmissible offer, all without a site call, since an override's shapes never merge with the live hint. An override still cannot tighten one hint listing's range without restating the pool's shapes, until an override can select the listings it applies to.

### Storefront pool overrides

A storefront is the final authority over what it sells within what a site declares. Its override for one pool at one site, in one offering mode, states shapes, settlement clauses, asking rates, and its market's commercial terms; it cannot state region or capacity backing, which are the site's, and its offering mode is never defaulted. Pool identifiers are site-local, so an override is keyed by site, pool, and offering mode, and a pool sold in two modes carries an independent override per mode, each wholly one market's.

The capability is a market-neutral storefront kit, `kit/pool-overrides`: the durable store and its reader, a write checked against the site, the status of each stored override, the signed-resource contract, a typed client over the core client's generic transport, and a framework-free route service. Each storefront binds that route service with its own router and administrator authentication, so the kit carries no web framework and makes no routing decision for a storefront. Each market contributes, per offering mode, the judgements only it can make: whether a record's shapes, rates, and terms are in its vocabulary, and whether a site's declarations are feasible for each shape. A market judges an override's rates through the same resolver publication reads them with, so a write it accepts is one publication can read, and the kit takes no dependency on the resource-pool kit. The core client stays universal, and a second market with shape requirements reuses the kit rather than copying it.

A write is checked against the site's resource-pool projection fetched live through the site's authenticated client, not against the storefront's held projection, so neither a stale generation nor a stale refusal decides it. A pool the site does not project is refused; an unreachable or unverifiable site is refused as retryable, distinctly; a shape no member is feasible for is accepted and reported, since delisting it is the intended effect. After an accepted write the storefront refreshes that one site's held projections, both families, without writing the live result into the held state itself, and wakes its publication loop, so the override takes effect promptly without a full reload; a failed refresh does not fail the write.

Bare metal joins the same store for the `bare_metal` mode. Its override states settlement clauses, asking rates, and lease bounds, and no shapes, because a whole machine's shape is its declaration. Clauses replace the configured publication clauses whole. Each lease bound replaces its configured counterpart independently, as configuration overlays do: replacing the pair as a unit would let an override stating only a minimum silently drop the configured maximum. Independent replacement can produce an unordered effective pair, since configuration states a maximum and no minimum. So a write is checked against the configured maximum, and publication checks again because configuration can change after the write; a conflict holds the pool under its own reason, distinct from an override that cannot be read, because the stored record is valid and only its combination with current configuration is not.

Override status is judged against the resource-pool projection the storefront holds for the override's site, which is the one reading of that site publication and the opening recheck also use; a site whose projection is not held is `unknown`, as it is just after a restart until the first poll loads it. Nothing durable records a projection generation for status. A bare-metal storefront database whose earlier publication runs recorded accepted generations keeps that table frozen and unread, under the storefront's frozen-table rule (`docs/development/DEPLOYMENT_AND_CONFIG.md`, "Migrations at startup"). The bare-metal override and publication commands call the running storefront's administrator API, signing with the storefront's own marketplace identity resolved from the configuration files the server reads, so they can act only as an identity the server would also be, and neither opens the storefront's database.

Derivation reads stored overrides itself, through the kit's reader, inside the derivation every structural-key reader runs. An override's shapes change listing keys, so publication and source reconciliation must resolve the same tier or reconciliation would close every listing an override shaped. The VM listings package names the kit in an optional `overrides` extra and imports it only on the projection path, so buyers, which install the package for its listing models, install neither the kit nor the resource-pool kit.

An override outlives its pool. Each stored override is in exactly one state: `site_unconfigured`; `unknown` while its site's projection is not held; `orphaned` while the held projection lacks its pool; and `applied`. An unloaded site is unknown, not absent, so an override is never called orphaned on the strength of an answer the storefront does not have. The override is the storefront's only per-pool tier: a term it omits resolves from the pool's hint and then configuration. A storefront that once also kept a pool-keyed record written by its own resource import no longer reads it, and carries none of its values over; the status report that named them is how an operator found the values to re-enter.

### Unknown sites and inline reconciliation

A configured site whose projection the storefront does not hold is unknown, not empty. Its listings are held — neither closed nor refreshed — rather than read as withdrawn, and nothing local stands in for the missing projection. Delisting would cost buyers the listing and registries a close and a reopen for every restart that raced a site; holding costs a buyer only an early refusal at round zero, where the inventory guard already refuses a listing whose site is not held. Holding has no time bound: a site decommissioned without closing its listings leaves them advertised until an operator closes them.

An operation that changes a site's capacity and reconciles inline — a VM administrator reservation, a fulfillment event, a failure action's release — refreshes that one site's held projections before reconciling, and reconciles against the same projection publication derives from. Otherwise it would read a projection its own change had just made stale, report nothing, and leave a later operation to report its closes as its own. The refresh belongs to the invoked operation, so a paused storefront stays paused and advances only by invocation, and it never wakes publication, because it reconciles the change itself. An operation that does not reconcile inline refreshes nothing: bare metal's administrator reservation and its capacity-released callback leave the held projections to the next poll.

A capacity event's reconciliation judges a fungible listing's availability on its site's capacity buckets, which move with the event, so it first refreshes that site's capacity-bucket family — every configured site's for a full reconcile — as an inline reconciliation does. The event's delta carries no bucket counts, and reconciling over the last poll's generation would leave a reservation's listing open for up to a poll interval, which close-before-reopen over availability-backed listings does not allow.

Each refresh path belongs to one category. A poll — the poller's cycle, the `site-projections` step, VM's administrator refresh route, and the drift check a topology-sensitive refusal triggers — wakes publication when a resource-pool generation changed. A refresh-and-reconcile — an inline reconciliation or a capacity event's — never wakes it. An accepted override write refreshes its site and always wakes publication. A poll arriving while another runs on a site's family joins it and returns its result; a refresh-and-reconcile waits for the operation in flight and then fetches, because it reconciles a change it has just made and needs a snapshot taken after that change. Either way a failed operation keeps the site's last generation as stale with its error and never counts as a confirmation. A wake never advances a held loop: a held publication loop stays held, and the wake makes it run promptly once resumed.

## Autonomous publication

VM and bare-metal publication each run as a lifecycle loop in the storefront's own process, not on an operator's command, and each cycle converges registries. A seller declares supply at their site, and the site's projection carries it to every storefront that trusts that site; one storefront can publish for several seller sites whose sellers hold no storefront credential. An operator-run command would leave a site's declaration unpublished until someone ran it, and an unbacked listing whose pool is withdrawn would stay advertised, since source reconciliation is the only reconciliation it gets. Each dedicated storefront publishes its own domain: the combined compute-family storefront publishes VM only, and one loop covering several listing types belongs to the storefronts' later convergence.

The loop follows the storefront's lifecycle conventions: the pause holds it with every other loop without affecting trading, one cycle can be run while held, and a dry run reports what that cycle would do and changes nothing. A change in a site's projection generation wakes an unheld loop. Terms come only from durable sources — pool declarations, the storefront's per-pool overrides, and configuration — because a cycle must be reproducible without the arguments of whatever command last ran. The loop builds only the publication sources of the domains it publishes, so a storefront can register another domain whose publication runs elsewhere. A publication command is a client of the loop: `market-storefront publish` and `bare-metal-storefront publish` run or preview one cycle through the storefront's administrator API, over the projections the running storefront holds, and open no database.

Every cycle records its outcome with the loop controller, naming the stage that failed — `compose`, `run`, or `converge` — and system status reports each loop's state and last outcome as `lifecycle`, so a publication loop failing every cycle is visible without reading logs. A recorded error carries its message only for the storefront's own configuration and publication errors, whose text names keys and reasons; anything else is recorded by type. Status also reports the latest derivation per site as `publication_derivation`, in one shape for both compute storefronts: each site's `holds`, `refusals`, and `reports`, every entry a reason code with the pool or Physical Resource it concerns and its detail. One `kit/capacity-publication` `SiteDerivationLog` keeps it for VM and bare metal, so the rule for what is recorded and logged has one implementation. Only a publication cycle that ran records into it: a preview records nothing, and a listing-source check or a capacity event's reconciliation has no cycle report to record, so status always reports what the last publication cycle derived, the cycle whose outcome `lifecycle` last reports. Each publication source keeps its own derivation of a site, so two sources composed in one process never clear or raise each other's entries. A configured site no cycle has derived since start is absent, so a site present with empty lists means a clean cycle, and a cycle that derives no site leaves each site's last derivation as it was. When a cycle cannot read a site at all — its projection is not held, or the domain refuses the generation — the site's hold names no pool, and the pool entries of the last derivation that did read the site stand beside it, since they still describe the pools whose listings the hold keeps; they clear only once a cycle reads the site again. Letting them clear would log every pool's entries as cleared at each outage and raise them again on recovery. The log writes each entry as a warning when it first appears in a site's derivation and at info when it clears, so a standing condition is logged once rather than every cycle; an entry's error text is not part of what makes it the same entry, so a standing hold whose source answers differently each cycle is not logged again. The error text a site's hold or a projection family's `last_error` carries may name the site's URL; site URLs are public configuration, and one carrying credentials is refused when configuration loads.

Bare metal composes the loops as VM does, with choices of its own. Its runtime builds the projection state and the publication wake; steps register when the runtime is built, so every lifecycle route can run one, and timers when the server starts, after the first poll. A cycle that cannot be composed raises `BareMetalPublicationError`, naming what is missing, and the source-confirmation window is resolved once at composition, where VM reads it at each check. Bare metal's stop hook stops and awaits every timer, so no cycle runs on against a runtime its application has uninstalled; VM's and the API-credit storefront's stop hooks leave their loops running until the process exits, which is a current limitation rather than a rule.

Missing defaults never refuse startup, because a storefront's terms may live in its pools. A bare-metal pool that resolves no positive lease bound from its override or configuration is held and reported in the derivation as `pool_lease_bound_missing`. A pool that resolves no settlement clause from its override, hint, or configuration has candidates with no settlement option, so they are refused as `no_settlement_option` and an open listing among them closes through reconciliation, reopening once a clause resolves (see "Reconciliation"). A storefront that cannot publish at all refuses to start (see the [specification](spec.md)).

## Durable seller close

Every close records whether its seller or reconciliation made it. A seller's close is enforced at the listing write every reopen passes through, not by each domain's reconciler: a write that would reopen it is refused unless the seller asks, and a later reconciliation close keeps the seller as its reason. Enforcing it once at that write is what keeps a domain that forgets the rule from undoing a seller's decision on its next capacity event.

## Registry convergence

For VM, API-credit, and bare-metal publication, the local listing is the publication decision and registries follow it, through the capacity-publication kit's runtime. A new listing is recorded locally, with its binding, before any registry is told of it, so no registry can hold a listing the storefront has no record of. A close or reopen changes the local listing first, so a registry never holds a state the storefront has not decided, and a local change that fails reaches the caller with no registry told. Each registry's outcome is recorded per listing, and every publication pass resends to any registry whose recorded outcome disagrees with its listing's local status exactly what that status implies, and only to that registry. The records are the repair source, so no separate journal exists, and a registry that stays unreachable remains diverged for the next pass. VM's and bare metal's publication loops both drive their cycles through the capacity-publication kit's cycle driver and end every pass with its convergence step, so the repair rule and how a pass reaches it have one implementation; each domain keeps only what its cycle derives, closes, and holds.

## Stable subjects and canonical principals

Storefront records distinguish durable market subjects from credentials. Listings retain their listing identity and storefront ownership context; negotiation threads, messages, accepted terms, settlement plans, heartbeat evidence, claims, obligations, and audit records carry the exact canonical buyer, seller, sender, payer, claimant, or actor principal appropriate to the record. Administrator and service-peer records similarly bind a complete principal to a named subject and role.

This separation prevents address-shaped data from silently becoming authorization. An explicitly named EVM recipient or transaction signer belongs only to a tagged chain-mechanism payload. It cannot replace the marketplace principal that owns a listing, participates in negotiation, or authorizes a storefront route. Consequently Ed25519 parties can complete non-EVM storefront paths while an Alkahest adapter can still consume independently configured EVM effect fields.

## Trusted site routing

`site_id` is storefront-owned configuration bound to one exact provisioning authority URL, an HTTP(S) origin, and to exactly one service peer. Authority URLs are public configuration, kept out of reprs, site diagnostics, and public results; a site's error text in status may name one, as "Autonomous publication" says, and credentials enter only through signer injection. Listing reconciliation freezes the trusted site and Physical Resource in an immutable common binding, and accepted negotiations copy it before agreement artifacts are stored.

Every client that talks to a site authority verifies its responses against that site's peer: the capacity clients, the per-site fulfillment clients, and VM's early lease termination, which goes through the per-site fulfillment client to the site the reservation is recorded at, as bare metal's teardown does. No storefront-wide provisioning trust set remains; a VM configuration stating `[provisioning.identity]` is refused at startup as removed. A site client reads its trust from memory at each response, through a provider the site and provisioning clients accept in place of a fixed set, so a rotation reaches verification as it commits and no response verification touches the database on the event loop. A reload of the trust that fails after an identity change committed never fails or masks the change: the trust drops the records it held, which predate the change, so every read refuses with 503 from memory, and a background reload retries off the event loop, waiting longer after each failure, until one succeeds. Reloads take one lock and read durable state while holding it, so a slower reload never installs an older load.

Bare-metal fulfillment reloads this binding for every step. Site-targeted capacity reservation, scheduling, fulfillment begin/status/result, teardown, and capacity release use the configured client selected by the recorded site or the durable reservation-to-site map. A buyer assertion, provider response, or opaque artifact cannot replace the site, URL, principal, Physical Resource, machine, or physical-host identity. Restart therefore changes neither authority nor executor, and capacity is released exactly once only after authoritative teardown succeeds.

The result channel is pull-based: the storefront polls the recorded fulfillment and converts its versioned bare-metal envelope to a durable buyer-safe receipt and credential-free access result. Provider payloads, private SSH material, authority URLs, credentials, and connection coordinates are not copied into market state, evidence, listings, or run logs. A separate buyer-authenticated access read re-fetches the active selected-site result and returns only the transient SSH host, port, public tenant user, and lease expiry. It is unavailable after teardown begins and is never persisted by the storefront.

## Role and service-peer identity

The storefront authenticates publisher, buyer, administrator, and service-peer traffic through the shared version 2 identity contract, then authorizes the complete principal against an explicit role and durable subject binding. A missing or invalid proof never falls back to an address, administrator key, private-key field, query value, listing field, or negotiation record.

At the route boundary, storefront code supplies the expected role, semantic operation, stable resource, and exact principal or active principal set from trusted context. The proof binds those values with the caller principal, method, request ID, timestamp, and canonical body hash. This makes reverse-proxy paths and untrusted body fields irrelevant to trust selection and prevents mutable request content from escaping the signature.

Replay reservation is authority-owned persistence, not an in-memory timestamp check. After cryptographic verification and before handler dispatch, the storefront atomically claims the complete principal and request ID with the semantic request hash and a bounded execution lease. Changed reuse fails closed. An exact retry can recover a completed outcome or observe an in-flight reservation without dispatching a conflicting mutation, including after a process restart.

Administrator and service-peer configuration contains public trust pins, but durable storefront state owns authorization after initialization. Configuration may create a subject only when it supplies one initial primary principal; later startup checks that configuration covers the durable primary and any active overlap rather than overwriting them. A subject keeps one role, a service peer also keeps one operator-owned `site_id`, and one principal cannot be active for two subjects at the same authority.

Provisioning and other service-peer connections are therefore pinned by both the active principals of a stable peer subject and the storefront-owned `site_id` binding. Signed requests, responses, and callbacks must match those exact pins before their contents affect routing, capacity, fulfillment, or settlement state. A peer cannot self-assert a different site through a body field, and matching identifier text under another scheme is not equivalent.

A seller may deliberately reuse one public principal for registry publication, storefront ownership, negotiation and marketplace settlement requests. That does not merge authority roles: every receiving service enforces its own binding and receives only a signer operation or signed proof. Storefront rows and projections carry the public principal and public mechanism references, never a private credential or provider identity.

Site trust comes from each site's service peer, in both compute storefronts. Configuration binds every site to exactly one `[Identity.service_peers.<peer>]` and seeds the peer when the server starts; from then on the peer's principals are durable identity state, rotated through the storefront's identity routes, and startup refuses configuration that no longer names the peer's durable primary and every principal active in an overlap. A restart after a rotation therefore needs configuration naming the replacement, while the rotation itself reaches verification when it commits, not at a restart. Responses and callbacks are verified against the same active principals, so a rotation never leaves the two disagreeing. Every site has its own peer; a principal of one site's peer cannot authenticate another site.

A callback names one site and is verified against that site's peer alone, refused with the trust's own reason when the site has none. The service-role read of system status names no site and returns readiness alone, so both storefronts accept it from the union of every configured site's active principals, skipping a site the trust cannot answer for, and refuse it as unavailable only when the trust can answer for none; requiring a single configured peer would refuse every site's readiness probe on a multi-site storefront. Bare metal serves VM's identity routes — rotation, completion, and status — committing through the trust. Its administrators are configuration and never a durable subject, so a rotation naming one is refused as not registered. A bare-metal reservation pins its site's peer subject; the principal recorded beside it, the peer's primary when the reservation was made, is an audit record never compared, so a restart after an authorized rotation keeps the reservation bound to its site.

Storefront clients verify version 2 mutation responses before accepting an acknowledgement. The response proof binds the expected authority principal, originating request identity, status, timestamp, and canonical body, so a valid response from a different authority or an altered transport body fails closed. The storefront applies the same contract when it signs administrator and service-peer mutation responses, allowing callers to authenticate the acknowledgement rather than trusting transport success.

Rotation preserves the stable authority subject. A site authority, storefront administrator, or service peer changes principal only when the active and replacement principals sign the same bounded canonical intent. The storefront applies identical intents idempotently, records primary, overlap, retired, disabled, and audit state, and accepts both credentials only during the overlap. Retirement is tied to the recorded rotation and old principal; expiry or explicit retirement removes old-principal authority, while disablement can stop a credential but cannot manufacture replacement ownership.

## Atomic storefront identity state

The storefront validates and migrates listing sellers, negotiation parties and messages, accepted settlement plans, heartbeat parties, obligation parties, administrators, service peers, replay reservations, stage events, claims, and audit actors as one service-local transaction. It cross-checks listing ownership, storefront URL, party relations, embedded principals, and uniqueness of active bindings before retiring address-only columns. Stable listing, negotiation, obligation, fulfillment, service-peer, rotation, and operation identities survive the conversion. A malformed or partial identity, conflict, duplicate binding, or referential gap rolls the whole population back rather than leaving a mixed authorization boundary.

## Settlement option reconciliation

The storefront owns seller settlement status and administration because it is the authority that turns mechanism readiness and seller intent into market-visible options. It preflights every enabled installed registration and passes complete typed publication clauses only to their owning ready builders. Options follow configured mechanism priority and source-clause order. A sanitized blocker suppresses only its unready mechanism; ready peers with valid clauses remain publishable. An enabled mechanism with no clause publishes nothing, and one clause's scalar price never supplies another mechanism.

Configured defaults, pool-declared hints, storefront pool overrides, projected reconciliation records, and direct listing requests converge on the same typed clause model before builders run. A pool override's clause list replaces configured defaults for that pool as a whole. Rates are human decimal asset quantities at input and are normalized exactly once by the owning mechanism to currency minor units or token base units; non-exact conversion fails rather than rounding. Legacy publication configuration uses an explicit preview/write/backup migration, and ambiguous multi-mechanism scalar pricing requires manual resolution.

A listing that publishes an Alkahest option advertises, in its `demands`, the release condition its escrow will use on each chain: the arbiter and its demand data, derived by `kit/alkahest` from the seller's `[Settlement.alkahest]` policy, the seller wallet, and the chain's address book, identically in every domain. Each domain derives them where it builds the listing, after readiness, through `kit/alkahest`'s `escrow_release_conditions`, which takes the escrows being published and the readiness they were published under and derives nothing for an unready mechanism: VM from its compiled clauses and the escrows an operator's create supplies, bare metal from the Alkahest options it built, API credits from the escrows its clauses compile and those a listing request supplies. An unusable Alkahest section therefore yields no condition and no Alkahest option on any path, and costs the seller Alkahest rather than the storefront's other mechanisms. A listing request cannot supply `demands`: a listing advertises only what the storefront's own `[Settlement.alkahest]` configuration can settle. A domain declares the release models it can deliver — API credits `recipient` only, bare metal `recipient` and `oracle_gated` — and a configured model its domain cannot deliver makes Alkahest unready with a configuration blocker naming it, rather than refusing startup: settlement verifies an accepted deal against its committed plan, so no settlement or collection path reads the section's current model. The advertised condition is what a buyer's proposal is authorized against when the seller materializes the deal's plan (see the [negotiation protocol](../negotiation-protocol/spec.md)); a listing advertising none on a chain fails closed there, and the escrow-shape guard rejects it early with its own reason.

An unbacked listing publishes only options its domain does not fulfil through capacity, because nothing would admit the deal they settle. Whether a mechanism fulfils through capacity is a required `fulfils_through_capacity` attribute of each domain's seller stage-table entry, beside the stage it describes rather than in a separate map that could drift from it, and publication asks the binding's delegate, through `admissible_settlement`, which clauses to keep: all of a backed listing's, and only those whose mechanism does not fulfil through capacity for an unbacked one. A listing left with no publishable option is refused whatever its backing, rather than published unbuyable, and whether its open listing then closes or is held depends on why each mechanism of those admissible clauses published nothing (see "Reconciliation"). That is what a readiness blocker's kind is for: a mechanism with any configuration blocker is ruled out by configuration, as is a contact-only option whose origin has no contact, and one whose every blocker is a reachability blocker is unknown, as `MechanismReadiness.unknown` in `kit/settlement-runtime` defines it once for every reader (see the [settlement configuration architecture](../settlement-configuration/architecture.md#readiness-publication-and-selection)). A clause naming a mechanism whose section is absent or disabled is dropped wherever it is stated — a pool hint, an override, or the storefront's own configured clauses — and rules that mechanism out, so a listing it alone priced closes in either domain.

Readiness recovery may add a deterministic option without changing listing identity. Loss of readiness may remove that option from future offers, but accepted Terms remain pinned. Seller operations live under `market-storefront settlement`: the common status command is observational, while mechanism-owned subcommands expose genuine differences such as an Alkahest check without creating separate publication paths.
