# Testing and Compatibility Architecture

The [normative contract](spec.md) defines established test boundaries. This document explains how each test level contributes different evidence and how asynchronous cross-service flows remain deterministic.

## Test jurisdiction

Use the lowest level that can prove the behavior:

| Level | Primary evidence |
|---|---|
| Unit | Pure transformations, validation, state transitions, and policy with injected collaborators |
| Service integration | Persistence, dependency wiring, HTTP mapping, authentication, retries, and one service's client behavior |
| Contract/conformance | A shared producer/consumer session or carrier interpreted by independent implementations |
| Smoke | Deployed reachability, basic configuration, and stateless wiring |
| System/e2e | Major lifecycle contracts spanning deployed authorities |

Higher-level tests do not repeat every lower-level branch. They prove that independently tested components compose through their public boundaries.

## Producer and consumer contracts

A cross-package fixture is an executable contract. The producer owns a minimal canonical builder and validates its own output; consumers validate required semantics while tolerating nondeterministic identifiers or timestamps. Shared fixtures live in an installed owning namespace so tests exercise package boundaries rather than checkout-relative files.

Use a shared fixture only when independent implementations must agree. The API-credits middleware conformance session is the clearest current example: Python, TypeScript, and Rust gates consume one observable protocol while keeping implementation internals separate.

## Deterministic asynchronous seams

A sleep is not evidence that a lifecycle transition occurred. Deterministic asynchronous tests use one or more of:

- an observable accepted/queued state;
- a server-side wait or long poll;
- a test-control gate that pauses execution at a named boundary;
- a public or test-only event/status surface.

A gate allows a test to assert the intermediate state before deliberately permitting completion. Test controls remain separate from buyer/public APIs and must not become production authority.

## Staged system tests

A staged scenario names each produced field and each downstream prerequisite. Consumers require the exact state they use and skip clearly when an upstream stage did not produce it, avoiding cascades of misleading failures.

The VM full-deal coverage uses complementary vehicles: a controlled flow gives precise assertions at intermediate boundaries, while a real buyer-CLI flow proves buyer-visible composition. Both traverse publication, negotiation, settlement, fulfillment, ready state, and release without making e2e own every component semantic.

Scenario fixtures create the precise resource and policy state they assert, remain idempotent across reruns, and clean up state that ordinary lifecycle timing cannot safely reclaim during the test.

## Boundary-change evidence

A moved or extracted boundary may require wheel-content checks, typing markers, dependency-direction tests, consumer suites, composition startup, duplicate-registration checks, and retry/idempotency coverage in addition to ordinary unit tests. Which checks apply follows the authority being changed.

For the VM storefront's injected domain boundary, focused tests register a compatible contract object distinct from the default in a one-registration registry and assert that the application, the lifespan's container, the repository, the listing service, and the negotiation runtime resolve the storefront's binding through that registry to that exact object, that the settlement composition refuses a contract its repository's registry does not hold, and that a second application built from another registry cannot start while the first holds the container and inherits none of its state. A contract of the wrong type, identity, or version, or with a missing declaration, an undeclared implementation, or an incomplete codec or hook set, is rejected by the root's validator, which runs before any stateful collaborator is built. The HTTP and package suites own observable workflow behaviour; restart coverage reopens a database holding real persisted identifiers under the same registry and confirms that the identifiers and the schema are unchanged.

Architecture tests inspect production imports and package metadata rather than test monkeypatch patterns. The repository check, `make check-architecture`, holds the layer, scope, and kind rules for every package, including no concrete cross-domain import. Per-package architecture tests hold what it cannot express: one default contract construction site, no lower-layer singleton accessor, which module of a package may import what, and an installed dependency on the lower-layer contract package.



## Multi-domain storefront evidence ownership

Core tests own contribution discovery, frozen registry invariants, exact-object resolution, schema-opaque carriers, publication fan-out, immutable bindings, and cross-swap rejection. Domain suites own selected-site adapters and payment receipt gates. Bare-metal live acceptance requires disposable hardware, real access and revocation, teardown, and capacity release; deterministic ports cannot establish those claims. API-credit suites own canonical key ownership, fulfillment-keyed grants, unknown-outcome retrieval, private credential delivery, and retryable issuance.

## Payment evidence ownership

SCM's credential-free suites exercise generated payment models, shared JCS vectors, mandate policy, signed receipts, accepted-state persistence, and domain composition through deterministic collaborators. A controlled VM smoke can prove pending → provisioning → ready with one delivery, but cannot prove a live ledger or hardware effect.

The payments service owns ledger accounting, fees, hold release/extensions and
cash providers; the dispute authority owns cases/rulings and applies their effects. A run against the in-lane doubles below is labelled *lane-double evidence*, with each double's installed contract hashes read from its status for information; only a hosted target yields *live evidence*. Pinned-vector conformance supports either and is not a third label; a kit's first-use evidence records the contract's published selection and content hashes, the target's selector and mode, the control trace it applied in order, and each buyer waiver, since a buyer that waived a term is no evidence of what a default buyer accepts. There is no third, proposed class and no contract mode: each double serves its kit's vendored publication only, and the doubles and their consumers are built from one wheelhouse and lock, so their contract bytes are identical by construction. A change that must build against an unpublished producer revision adds a mode then, against that revision's real shape. Consumer tests do not inherit Stripe claims or a signed hosted-release profile matrix. Complete-deal qualification that needs the payments service's internals (local ledger, development-mode auth, operator test funds, ledger reads) is owned by the payments service's own end-to-end tests, which import this repository's published packages; this repository does not import the private service to test it. This repository's live payment scenario targets a public payments test deployment through its public API, runs only when such a target is configured, and otherwise reports the unmet prerequisite. A live payment run records the actual service target, consumer revision, authentication method, seed state, and observed readiness. An absent or unready external payments target, or a missing physical target, is reported as an unmet prerequisite before scenario mutations, not converted into local acceptance. Once a payments target is configured, the settings a scenario supplies itself — its parties' accounts and credentials and the service policy it pins — are configuration the run owes, so a missing one fails the scenario, naming it, rather than blocking it: a run with no target stays a blocked skip, while a misconfigured payments run fails deterministically.

Live evidence of a rate deal is a boundary comparison. A live verification scenario gives a hosted authority the input its lane twin gave the double, produced by SCM's own client code, and holds the authority's output to the twin's shared assertion, which names the fields it compares exactly, by relation, or not at all; it tests nothing downstream of that output, which the twin proves against the double, and a different output fails the observation. The VM live scenarios compare the payments authority's outputs for the buyer's stop, funds running out, a spot preemption and the term end, and the dispute authority's for a seller's filing and a buyer's contested case ruled by a topology's policy ([`TESTING.md`, "Live verification"](../../../docs/development/TESTING.md#live-verification)). They depend on no endpoint the dispute authority's public client lacks: an operator's ruling is the authority's own, reaching a scenario only through a policy the topology applies, and the interaction between mediation and payments is qualified by the payments service's own live verification scenarios. Each states its topology requirements in prose, naming no infrastructure, and a requirement the topology does not meet leaves the observations needing it unproven.

### The in-lane payments double

The VM, bare-metal, and API-credit lanes each run a payments double, `tools/payments-lane-double`, so their payment scenarios run rather than skip. It is an HTTPS service over the payments kit's `PaymentsAuthority` engine — the engine the in-process `FakePaymentsClient` uses, so there is no second ledger — and it mirrors the payments service's API: its routes, bearer authentication, approval admission in the service's order, read authorization, the idempotent repeat of an approved mandate whatever the clock or balance, and the published `ApiError` codes. It serves whatever its engine serves, and its suite proves, through the payments kit's real client, both the once-only surface the lanes' scenarios use and the rate and hold surface: rate parts and payee-only `start`, `stop` with notice and the earliest pending stop taking effect when its injected time reaches it, per-part `end`, funding exhaustion at funded-through, `afterStop` holds, partial `reverse` before and after a stop, and `extend` and `lift` with their published refusals. Each compute lane delivers rate deals against it: the recurring purchase, the rate rows and the watchdog's delivered-deal cases ([`TESTING.md`, "The canonical compute deal"](../../../docs/development/TESTING.md#the-canonical-compute-deal)). The payments service's scheduler reserves a started rate part's further periods as time passes; the double runs nothing of its own, and takes that decision as an answer the scenario programs, through its reservation control, the scheduler's scenario-programmed stand-in ([`test-doubles.md`, "A double mirrors its producer"](../../../docs/guidance/engineering/test-doubles.md#a-double-mirrors-its-producer)). A rate part is reserved at approval, at `start` and at that control, never at a read, so once injected time passes the periods reserved, the next read shows the part's `terms` stop at their end. A double mirrors its producer unless there is a compelling reason to deviate ([`lane-doubles.md`, "A double mirrors its producer"](../../../docs/guidance/repository/lane-doubles.md#a-double-mirrors-its-producer)), because a double that answers differently proves only that a client agrees with the double.

Each lane's callers reach it at `https://payments-double:8443` under a committed lane CA they trust through their payments configuration's `ca_bundle_path`; its accounts, tokens, receipt-signing seeds and certificates are labelled public development values. The lane marks the target its own (`PAYMENTS.LANE_OWNED`), so an unready double fails the run by name rather than turning every payment scenario into a skip, and lane setup runs each payment storefront's `check-payments` from its own container before any scenario. A result against the double establishes that SCM's roles compose through the payments service's published HTTP contract from committed configuration. It establishes nothing about the payments service's ledger, funding or availability, or about live receipts: the double always signs `livemode: false`, so a live-configured role refuses its receipts, and its state lives in one process's memory for the life of the lane.

### The in-lane mediation double

Every lane also runs a mediation double, `tools/mediation-lane-double`, at `https://mediation-double:8443` under the same lane CA, and the lanes' registries recommend its identity as the dispute authority every payment deal names. It reproduces the dispute authority's API mechanics against the mediation kit's vendored contract: bearer authentication, schema validation, idempotency and conflict answers, the filing's admission checks (a filer who is no party, and an Agreement whose JCS SHA-256 is not the signed receipt's `deal`, both refused before any case is reserved or part extended), the closed-case refusal, appends with concurrence only from `mandate.to`, the signed per-Agreement record and its cursors, the respondent listing, protection by real per-part `extend` calls at the payments double as the authority's own account, automatic dismissal of a case whose every part is not held, and a ruling's per-part `reverse`, `stop` and `penalty` effects applied as payment events under stable effect keys, resumed after a payments failure without a duplicate, then the case's own extensions lifted. It takes every decision the authority would make — whether a case is ruled, its basis, delivery end and effects, a filing's answer — from a rule a scenario installs, the way mock provisioning takes a job's outcome. With no matching rule nothing is ruled, as silence never rules, so a payee-filed or concurred `delivery_end` claim the authority would rule mechanically is ruled only when a rule says so; the double's README states that deviation.

Two choices keep its answers honest without reproducing the authority's logic. Only payments' nothing-held refusal reports a part `not_held`; every other refusal and every transport failure answers the filing `protection_incomplete`, which a same-key retry completes, so a payments outage or a misconfigured authority account never tells a filer its money is not held. And the payments snapshot states no reason a part is not held, so the double classifies the part's signed amounts: `paid_out` when any money was released, which mediation cannot recover and a filer most needs to know; otherwise `reversed` when any was reversed or refunded; otherwise `nothing_held`.

It verifies no concurrence signature or mechanical guard: SCM's verification is proven in the kits against the producer's vectors, and a guard is the authority's decision logic. The Agreement's binding to its payment is the authority's admission rule instead, checked against the receipt the double already reads, and an honest SCM filing always passes it.

The double executes the effects the contract defines, while which effects a ruling carries stays the scenario's programmed rule. A `stop` is one stop event from the double's own account through the part's `chosen` stop entry, carrying the ruling's partial-period treatment and its time while that time has not passed; payments never backdates a stop, so a passed time is a stop now. Once payments accepts the stop, the double reverses to the payer the earnings beyond what a stop at the ruling's time would have earned under that treatment, as far as the part still holds them, attributed to the stop by its effect id, as the dispute authority documents a stop effect, and sends no reversal when there is none. A `penalty` is reversals of earned amounts still held across the transaction's parts in mandate order, read after the ruling's earlier effects, up to the penalty and no further than what is held. Each effect's events are kept once built and resent unchanged until applied, and are rebuilt only when payments refused an effect's first event that no earlier send can have delivered, since a kept stop whose time has since passed would otherwise be refused on every resend. A mechanical ruling of a payee's `delivery_end` on a rate deal therefore carries a delivery end, the `stop` and the `penalty`, and no `reverse` of its own: the stop's reversal covers the earnings since the end. An `award` is unexecutable on `arkhai.payments.v1`, so a rule or decision carrying one is refused at install. A ruled delivery end with no `stop` on a rate deal leaves the deal listed `ending` with its payment running, which is the authority's to correct, since SCM sends no money operation of its own; a future-dated ruled delivery end, which the producer documents none of, is not reproduced. Closing a case still applying a ruling is refused, since the contract's closed entry follows every effect's application and has no state for an abandoned one.

A rule's gate holds a ruling before its effects, the delivery end with them, so the ruled entry records the delivery end `prepared` until the rule is resumed. SCM's watch records an end from a delivery-end effect without reading its applied state, so the gate holds the delivery end only in the double's record: a scenario steps no storefront servicing while a ruling waits at its gate. What a `prepared` delivery end means is the producer's to state ([`ROADMAP.md`, Goal 8](../../../docs/development/ROADMAP.md#goal-8--sell-compute-by-the-period-until-either-party-stops)).

The double's identity needs no production guard: it is inert outside development topologies by construction. Its origin is only a lane-private service name, answered in a Compose lane or in a validation namespace whose own local values enable its subchart, while a release rendered from release values runs no double; its account's only token is at the payments double; and its record key derives from a committed seed labelled a public development value, never for a public network. Registries recommend it only in lane profiles and the local release, and a live deal naming it could only come from a buyer accepting it, which the buyer's acceptance list already governs. A loader guard would embed test values in production kits, and a copied lane configuration would copy its marker.

A lane result against it proves SCM's filing, answering, observation, end service and display of a ruling over the authority's real mechanics, not a remedy's arithmetic, which stays qualified by the producer's ruling traces, nor a hosted authority's availability or policy. SCM logic downstream of a side effect SCM cannot create live — the dispute authority's stop on a rate deal, which only a ruling makes — is proven against the doubles, whose limits are amended where that logic needs them: the VM lane's rate-deal disputes, a seller's filing ruled as the authority documents a mechanical ruling and a buyer's filing the storefront contests ruled by an operator decision, each show the authority's stop recorded and classified `ruling`, the payer's returns, the teardown and, once the case closes, the deal listed `ended` ([`TESTING.md`, "The canonical compute deal"](../../../docs/development/TESTING.md#the-canonical-compute-deal)).

### Lane time and the doubles' controls

Both doubles serve one typed control contract, `tools/lane-double-controls`, which the doubles, the API-credit sample app's time control and the end-to-end harness import, so the route models are written once and the harness installs neither double: when→then rules (a refusal with a published code, a transport fault, and at the mediation double a filing answer or a ruling with its gate), the mediation double's operator decision, close and case listing, the payments double's funding, receipt-signer rotation and rate-part reservation, rule listings, and each party's time control. The controls sit on each double's lane-private port behind a fixture token; a lane is its own stack and a rule's `match` is its scope, so there are no run identifiers. The inference gateway, a published package, serves the contract's time route and status on the same wire without importing it, and its suite drives it through the contract's client.

The reservation control, `POST /test/transactions/{id}/reserve` with `{"through": <Unix seconds>}`, stands in for the payments service's scheduler. It reserves each of the transaction's running rate parts — started and not stopped — through that instant, as far as the part's end and the payer's balance allow, by the arithmetic the engine applies at `start`, and answers each part's `reserved_through`, which the signed snapshot reports as its funded boundary. Funds running out is therefore a boundary the ledger computes, not the scenario's choice. A transaction with no running rate part — before `start`, once-only, or every rate part stopped — is refused `409 no_running_rate_part` and nothing changes, so a stage run too early or against the wrong deal fails where it runs instead of passing with nothing reserved. A reservation is a stage of its own, declared only where the double runs ([`test-doubles.md`, "Shared stages never depend on a double"](../../../docs/guidance/engineering/test-doubles.md#shared-stages-never-depend-on-a-double)): a rate row setting lane time past its deal's first reservation calls it first, and against the payments service its scheduler reserves instead.

A transport fault lives in the double, as shared middleware that starts a response and abandons it, so SCM's clients see a transport error exactly as for a lost response; a refusal with a 5xx would prove the wrong branch, since SCM's mediation adapter reads a 5xx as pending and a transport error as unknown. The middleware never faults the control routes or `/health`, so a finaliser can always remove the rule that caused a fault, and an orchestrator's liveness probe never restarts a double — losing every deal's state — during an outage. An outage is a rule with `match: {}`, never scoped: a scoped outage has no caller and would only drop some requests before commit.

Every party in a Compose lane perceives one lane time, which the scenario sets: both compute storefronts and the API-credits and inference storefronts, the provisioning services and the sites they host, every registry, the API-credits service and the inference service and the site ledger each hosts, the sample app and the inference gateway and the metering gate each hosts, both doubles, the chain, the buyer and the harness's own signing clients. Each reads the time of the world from its process's one source ([injected time](../injected-time/architecture.md)), configured for injected time in configuration only the lanes load. Lane time spans every party because every signed hop checks the other side's timestamp within a skew: a party moved alone breaks every signed exchange with a party that did not move, and one left on wall time cannot follow a state the others reached. With the doubles alone advanced, a stop the payments double records at an advanced instant is in every other party's future: the storefront schedules an end the site reaches only on its own wall clock, and the provisioning service stamps a termination earlier than the commanded instant, which the compute classifier rightly does not recognise. So the boundary of lane time is every party that signs, verifies or decides by time in the lane; widening the skew, a purpose-specific clock for authentication, and bending the classifier to a test clock were each rejected, as putting a test concern into production authority.

Injected time is frozen: every party holds the instant last set until the next set, so the parties agree exactly and nothing elapses unseen between stages. Lane time only moves forward and is never reset: each module continues from the instant the one before left, since a reset would move journals backwards and reopen replay windows once replay state is pruned against the clock. What is deterministic is the order of events, not a pre-chosen instant; a stage may set any forward instant, including the wall time plus an offset.

One session fixture, `lane_time` (`e2e-tests/tests/e2e/roles/helpers/lane_time.py`), sets every party. The run's profile names its mode and every party, so a party the lane runs but the fixture cannot reach fails the setup rather than skipping. At the session's start it reads first the parties it reaches with no signed timestamp — the registries' bearer administrator route, the controls, the chain and the buyer's file — and moves the harness's own source to the latest instant they hold, or the wall instant when that is later, before reading any signed status, so a stack an earlier run left ahead past the signing skew still answers; it then sets every party to the latest instant any holds, never setting one back. Exempting the administrator status read from freshness, which would widen the identity exception, and requiring a fresh stack for each session were rejected. A set moves, in order, the harness's source — so each signed setting request is signed at the new instant, which the time-setting operation's freshness exemption admits — each service through its typed client, both doubles and the sample app through `lane-double-controls`' client, the chain, and the buyer's time file, then reads every party's status and fails naming any not at the instant set, a status with no time section, an older image that ignores the setting, among them.

The chain follows lane time: Anvil stamps blocks with its own clock, and an escrow's expiration is compared both on chain and off it, so at the session's start and at every set the fixture freezes Anvil's block time (`anvil_setBlockTimestampInterval(0)`), sets its next block timestamp to the lane instant and mines a block, so every block until the next set carries that instant. The buyer, started afresh for each stage and with no API, reads its time from the time file its generated configuration names, on every read, which the harness writes with the time component's writer. The one buyer run in the harness's process, the watchdog's delivered-deal cases', has no `[time]` table and reads the harness's own installed source.

A run is on injected or wall time throughout: a frozen party drifts behind every real one, and signed hops and grants then fail, so the session reads every named party's status and fails naming a mix. Every Compose lane runs injected time; the API-credits and inference lanes are no exception, since the sample app's middleware and the inference gateway's gate sign every request to their authority and so share lane time through the host's control. The inference lane's model stub signs nothing and reads no time a party checks, so it has no time source. External-topology runs — the real-provisioning lane, whose relay plugin checks grant expiry on its own clock, and every run against hosted authorities — and the local Helm release run on wall time; giving the relay plugin a time control would put a test control in a security component and leave hosted runs on wall time anyway. Shared stages reach an instant through one helper either way, `LaneTime.reach`: an injected run sets lane time there; a wall run waits, bounded, only for an instant the scenario's own data fixes, such as the Agreement's start plus an offset the scenario chose, or one an authority recorded, in a signed record the stage read, as the effect of the scenario's own request — a preemption's effective instant, the funded boundary — and a stage needing any other instant is a blocked skip naming the wall-time target. A recorded instant is admitted because the authority fixed it in answer to the scenario's own input, so waiting for it measures that input's effect rather than a timer the scenario does not own. For an external component whose time a test does not control, the ladder is [`system-tests.md`, "Time a test does not control"](../../../docs/guidance/engineering/system-tests.md#time-a-test-does-not-control).

Each double reads its injected source, set through `POST /test/time` behind its control token, so authority timing — a notice stop taking effect, funding exhaustion, a payout after the dispute window — is reached by setting lane time, and due state becomes visible at the next read with no background work. The sample app, test-only and unpublished like the doubles, takes the same control behind a token from its own environment, excluded from its metering gate; the published metering middleware has no control and reads its host's source. A lane's time lives only in its own parties, so lanes running side by side, in separate Compose projects or separate Helm validation namespaces, never share it.

The VM lane's six dispute controls scenarios use the CA, the storefront's dispute adapter and the controls together, each on its own deal ([`e2e-tests/README.md`, "VM dispute controls"](../../../e2e-tests/README.md#vm-dispute-controls)); every other control is proven by its double's own suite through the typed client, so its first lane use runs over a client path those scenarios already prove.

## Lifecycle contract evidence

The payments kit owns installed JSON Schema/generated models, JCS/signature and
snapshot vectors, and one clock-injected per-part `PaymentsAuthority` fixture
engine. Its in-process `FakePaymentsClient`, its consumer fixtures, and the lanes'
HTTP payments double all use that engine; only the double can serve a buyer
subprocess or a storefront container. Mediation owns its
independently installed schema/models, both ed25519/eip191 claim vectors and
ruling traces. These fixtures prove deterministic public-contract compatibility,
not the internal implementation or deployed monetary execution of either service.
SCM imports no authority service implementation.

Unit/service suites own same-key retry, lost-response adoption, caller-session
admission/end races, exact-envelope capture, pinned-authority verification,
independent cursor floors, respondent answer journals and conservative retention.
Site/provisioning producer integration tests own atomic rollback of the ending
transition, its event and its signed report, all ending causes, crash/ack
recovery, exact signed push/pull after signer change, unsupported-peer parking and
explicit resumption, and the carrying of an earlier release's pending deliveries
into the event store. Consumers do not replace that
producer proof with a hand-built report.

Restart recovery of rate deals is proven at application integration
([`test-levels.md`, "Integration tests"](../../../docs/guidance/engineering/test-levels.md#integration-tests)):
each compute storefront is stopped and composed again over the same database,
each case on a delivered deal of its own — a running rate deal, an ending deal
whose buyer stopped while the storefront was down, and a spot deal with a pending
seller stop — and the restarted storefront's loops are stepped through its typed
admin client and the deal read through its typed lifecycle client and its
records, with the payments service the payments kit's in-process engine behind
its client, outliving the storefront with its records
(`domains/vms/storefront/tests/integration/test_restart_recovery.py`,
`domains/bare_metal/storefront/tests/integration/test_restart_recovery.py`). The
running deal stays served with no end recorded and nothing re-driven, the ending
deal's end is recorded only once a servicing cycle reads the buyer's stop, and
the seller's stop is recorded at its instant, not before. Both storefronts rebuild their servicing
from the database and the authorities' records; the site is a fresh fake, so
these cases assert what the storefront records, not the site's teardown.

Deployed VM and mock-bare-metal scenarios distinguish receipt-time surrender,
retrieval of the original signed site report before teardown, and later proven
capacity return. Mock provisioning proves no physical access or revocation.
Once-only payment/case encounters prove no rate stop, funding or monetary ruling
execution. A configured real authority and, for physical claims, a disposable
real host remain qualification prerequisites. Readiness failures and unrun lanes
are named, not converted into fixture passes. See the
[lifecycle limits](../deal-lifecycle/architecture.md#current-limits).

## Ordinary Arkhai purchase evidence

A physical qualification can drive the shipped ordinary buyer and collect independent observations through the supported typed operator clients. Keep buyer credentials separate from operator credentials and bind each run's source, selected artifacts, configuration, buyer result, Agreement/payment evidence, reservation, fulfillment, provisioning jobs, and access observations in restricted evidence. Public summaries should retain only sanitized outcomes and explicit limits.

A completed payment proof correlates genuine TEST funding evidence with attributable rental charges and the accepted Agreement/receipt state; pre-existing unexplained credit is not funding proof. The receipt gate and seller/provider lifecycle observations establish distinct facts. Paid buyer journeys are required for claims about the actual tenant identity, negotiated privilege, valid grant, GPU work, delivery, ordinary teardown, fresh access denial, and restored capacity. A supplemental network-policy probe is admissible only from an actual operator-only CPU guest on the same paid deployment, using the pinned guest base, its actual default bridge and virtio NIC, and the loaded policy structure. It may establish only the finite selectors observed on that path; it establishes none of the paid tenant identity, credential, privilege, grant, GPU, payment, delivery, or lifecycle facts and does not prove universal isolation. A namespace-only probe is not a substitute for this guest-path evidence.

The ordinary buyer method may replace a payment-specific scenario driver, but it does not make an old named test marker pass. Preserve unrun or unavailable observations explicitly, and do not equate a controlled local smoke, published vector, or component suite with external funding or physical access.

The ordinary buyer method is also written as scenarios. Each compute lane runs a buyer purchase through the shipped CLI in `arkhai.payments.v1` against its payments double: VM's ends by a back-dated lease and a stepped watchdog cycle, bare metal's by the buyer's `end` before the seller's refund. The real-provisioning qualification modules make the runbook's observations 2, 4, 5 and 6 against a configured real-provisioning target and payments target: those of observations 2, 4 and 5 extend those purchases, adding only the real-host stages, and observation 6's makes no deal, reapplying registrations on the stack their purchases populated ([`deal-scenarios.md`, "Locally verifiable and external-topology scenarios"](../../../docs/guidance/repository/deal-scenarios.md#locally-verifiable-and-external-topology-scenarios)). The scenarios are the method a candidate's qualification reaches for first; the operator-run method above remains accepted beside them.

A purchase scenario checks each transaction against its records — bound to its Agreement, its receipt over that mandate, its snapshot naming the configured payer and payee with gross equal to the Agreement's price — and checks the payer's account by a balance sum: the drop in the payer's `available` balance, read through the payments kit's `get_balance` with the buyer's own token, from before its first purchase to after its last approval, equals the sum of its own transactions' debits. The sum proves the scenario's debits account for the drop, not that nothing else debited the account, so it rests on a precondition the scenario cannot check: the payer account is dedicated to the run, which is the deployment's guarantee, stated beside the result. Proving exclusivity would need a payer-scoped debit listing, which the payments service does not offer. Funding and its proof are the deployment's, joined to the run by transaction identifiers.

An `arkhai.payments.v1` option is published only with an accepted dispute authority, and every mandate names that authority's account. A deployment running the qualification pins an authority identity whose account is real at its payments target, and nothing needs to answer at its origin: servicing records an unanswered authority and continues. The lanes' registries recommend the mediation double, so the bare-metal buyer's `end` files a delivery-end case that is accepted and held per part with no rule; the scenarios read it as a filed case, never as a ruling or as delivery, access-end or refund evidence.

Each compute lane also runs one recurring purchase, `e2e_vm_recurring_purchase` and `e2e_bare_metal_recurring_purchase`, as lane-double evidence, delivered and ended by the buyer. The lane's storefront configuration alone declares rate servicing, for `charged` and `returned`, and the seller publishes a recurring on-demand option whose approval window, delivery deadline and one period fit within its maximum duration. A default buyer buys it through the shipped `buy`, which approves and commits in one run, so the scenario asserts the published per-period price, the accepted money the buyer prints — per-period charge, setup, initial reserve and maximum end, whose order before approval each buyer's own test proves — and an approved mandate whose single rate part charges one period's price. With lane time at the Agreement's start and delivery recovery stepped, the site activates the lease, the payments double records the rate part's start after that activation, and the deal becomes available. A minute into the first period the buyer ends it by its own `end`: the payer's stop is accepted at the payments double and charges the started period, its hint makes the storefront read the payment authority and record the payer's stop as the deal's end before the deadline, with no `delivery_end` filing, a servicing step carries that end out at the site and the teardown completes, the payer's balance is down by exactly one period's price, and the seller's list shows the deal `ended` once the release is proven. The seller's refund refuses a rate deal, so a failed run's cleanup ends an approved deal by the buyer's own `end` too. The rate rows — funds running out, a spot seller's preemption and the maximum term — and the buyer watchdog's delivered-deal cases run beside it in both lanes, on lane time, as lane-double evidence ([`TESTING.md`, "The canonical compute deal"](../../../docs/development/TESTING.md#the-canonical-compute-deal)).

A real-provisioning scenario pins a VM or bare-metal host only from an independent source: the target's stated `ssh_host_public_key`, or, for a VM host, a pin already stored, an earlier run's or one an operator captured after comparing the presented fingerprint. With neither, a VM scenario refuses before declaring capacity, naming the field. It never captures the key a host presents, since comparing an observation with itself is trust on first use, and its jobs would then send the relay token and a buyer's keys to whatever answered ([physical-provisioning, "The host registry owns the connection"](../physical-provisioning/architecture.md#the-host-registry-owns-the-connection)). The target's key stays optional, so a profile for a host already pinned keeps working, and a reapply restates the pin held at registration and checks the management pins retained.

## The real-host proof of guest isolation

`e2e_vm_guest_isolation` proves VM guest isolation ([physical-provisioning, "Guests are isolated from each other"](../physical-provisioning/architecture.md#guests-are-isolated-from-each-other)) on a configured real-provisioning target. It is an external-topology module of its own, in no lane, that subclasses `e2e_vm_real_provisioning`'s stages and fixtures: it makes the same two deals on one host, adds its isolation stages within the window in which both guests run and the first holds a heartbeat, and shares that scenario's recovery and teardown. Isolation stages inside the real VM scenario itself would restart libvirtd and alter a guest in every ordinary real-provisioning run whose target names the section, blurring that scenario's evidence, and guests created with no deal would have no buyer session to show a claim or a convergence leaving it uninterrupted.

**The operator route.** Restarting libvirtd, reloading UFW, reading the guest policy's chains and counters, planting a guest unconverged and running the convergence are no product operation, and nothing a test is offered does them. The module performs them through a harness-local operator route the VM target names in its optional `guest_isolation` section — the route's address, port, user, and the path of a key the harness references and never copies — as the bare-metal qualification's `cleanup_qualification.operator` is. The operator code is one fixed Python probe beside the scenario (`guest_isolation_probe.py`), carried with JSON arguments over the shared SSH seam and run as `sudo -n -- python3 -c <probe> <arguments>`. The route gives the test no reach the deployment lacks, since the provisioning service already holds a key that runs code as root on the host; it gives the test a route of its own, apart from the service's. Without the section every host-side stage skips naming it. Guest-side probes are the same program, run in each guest through its buyer's SSH session, under `sudo` with the tenant password the deal delivered to that buyer: raw ARP, ICMP and DHCP frames, a gateway route and the guest's redirect setting all need root there.

**Attribution.** A refusal in O3 to O5 counts only when the matching policy rule's packet counter, read through the operator route before and after the probe, rose, so a destination that does not exist is never read as refused, and neither of the target's two private destinations needs to answer. The listed destination counts as forwarded only when its accept counter rose and the guest's packet to it was seen leaving the host: while the guest probes it, the operator probe holds a packet socket bound to every protocol on the interface `ip route get <listed>` names, since Linux hands a transmitted frame only to packet sockets bound so, and counts the guest's outgoing TCP to that address after masquerade. The counter shows the policy admitted the packet; only the egress shows the host forwarded it past every other table's chain at that hook. Counters are per rule, so the run's guests are expected to be alone on the host, a precondition the controlled target guarantees and the run states beside its result.

**The planted fixture.** Convergence is proven on the first deal guest, the one holding the heartbeat, planted with the state a guest isolation never reached would hold: its tap's isolation cleared, its filter detached live, and its saved definition stripped of both. The module then runs the host kit's installed `arkhai-guest-converge` and reads its lines, as host preparation does, so neither caller interprets `virsh` itself. Clearing a live port's isolation and editing a saved definition are always allowed, so O8 can be planted on every libvirt; whether the filter is bound live again is O9, observed apart.

**The outcome.** The module logs each observation, O1 to O9 as the specification lists them, as made, failed or unproven after its last stage, through the qualification modules' helper, and the run logs the host's libvirt version. O6, a buyer from a private address reaching their guest, is read from the buyer session's peer address in the guest; a VM create masquerades a forwarded buyer connection, so under direct access the guest sees the host's own address on the guests' network and O6 is unproven naming the masquerade, as it is under relay access naming the route it lacks. Its replies' passage then rests on the forwarded established/related accept's place ahead of the private-range drops, held by the rendered-chain and installer tests, and on O7's evidence that the chain order survives on a real host. O9 is unproven, naming the libvirt version, only when libvirt refuses the fixture's live filter removal or convergence leaves the filter for the guest's next start with the live definition not naming it; a live update libvirt took but did not bind fails it. A run's evidence is supplied by whoever deploys the target as a sanitized summary per observation, with its run identifier and the host's libvirt version; raw logs stay in the operator's storage. The run's prerequisites are the validation runbook's ([`VALIDATION_RUNBOOK.md`, "25. Run The Real-Provisioning Scenario"](../../../docs/development/VALIDATION_RUNBOOK.md#25-run-the-real-provisioning-scenario)).

O7 shows each jump first in its built-in chain and the policy's decisions holding after a libvirtd restart and a UFW reload, not that a refill left nothing behind: the scenario reads only each built-in chain's first rule and the first matching rule of a chain, so a leftover duplicate jump or doubled rule, which would decide nothing differently, would pass. The module probes no IPv6; the guest policy's IPv6 drop rests on the installer's tests and on the same jump-first mechanism the IPv4 observations show.

## Current limits

The e2e harness predominantly uses HTTP clients and explicit test seams, but it is not yet completely external to service packages and a few scenarios retain private-client dependencies. Compute pipeline scenarios advance only by their own steps ([spec](spec.md#requirement-pipeline-scenarios-advance-only-by-their-own-steps)); the API-credit lane steps its storefront's chain probe and listing seed but holds none of its loops, so an unstepped timer can still run beside its stages; the real-host scenarios, which run outside every pipeline lane, still poll the hardware they drive. The architecture therefore states the desired boundary only where current tests establish it and treats full harness extraction as separate work.

Repository-wide typed-client ownership, universal sync/async parity, and a closed list of raw-HTTP exceptions are not established baseline guarantees.
