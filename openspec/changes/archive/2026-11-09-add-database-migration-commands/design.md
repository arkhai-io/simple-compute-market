## Context

Six services own SQLite state: compute provisioning, the VM storefront (`market-storefront`), the bare-metal storefront, the API-credit storefront, the API-credit service, and the registry. Only compute provisioning separates migration from startup: `compute-provisioning-migrate` runs as a Helm init container, and the application refuses a database behind its chain. Even it is a hybrid — `create_all` over seven metadata sets runs around its versioned chain, its guard checks only that the last listed ID is recorded (so a table added without a migration, or an ID the code does not know, passes), its refusal names a `migrate-job.yaml` that does not exist, and no render test covers the init container.

The three storefronts build their schema whenever `core_storefront.SQLiteClient` is constructed. `_ensure_tables_sync` interleaves an unversioned bootstrap (legacy renames and drops, about thirty `try/except` column additions, backfill-then-drop sequences — still extended as recently as 2026-10-08), `CREATE TABLE IF NOT EXISTS`, two passes of the core chain (the first silently skipping, without recording, any migration whose `required_tables` are absent), the kit and domain chains, domain indexes, and domain refusal checks. `kit/deal-servicing`, VM's delivery records, and bare metal's lifecycle cursor create tables whenever a store opens. One core migration (`20260811_001_marketplace_principals_v2`) needs the configured principal and storefront URL, so the storefront chain is not configuration-free.

The API-credit service runs `create_all`, seeds a `default` pool, and applies a versioned chain in-process; its `check_schema_version` exists and nothing calls it. The permanent spec names it as allowed to migrate in-process. The registry runs Alembic in-process (`create_all` + `stamp head` on a blank database, legacy-revision detection otherwise). Both storefront charts' render tests assert that no init container renders.

Four engines exist: provisioning's (SQLAlchemy `Engine`, records each ID in a separate transaction after the migration), the API-credit service's copy of it, core storefront's (`sqlite3`, one savepoint per migration with its record inside), and the registry's Alembic.

The marketplace v0.3.0 release (`main` at `d595f0c2`) carries exactly dev `9fffe41e9`'s service code. An upgrade of a long-lived deployment to v0.3.0 found that the v0.3.0 provisioning chain itself writes legacy hosts as `ssh` connection version 1, which v0.3.0 refuses, so every job dispatched to such a host fails before any playbook runs and a release attempted on one is left `release_failed`; and that the bare-metal storefront left a superseded listing open at the registry, unknown to it.

## Goals / Non-Goals

**Goals:** one migration mechanism for every stateful service — a packaged command, a startup check that issues no DDL, a deployment phase before the application, and a `--check` preview; a chain that begins at the v0.3.0 schema, so pre-release history and its bootstrap are deleted rather than carried; atomic per-migration recording; supported v0.3.0 databases adopted and repaired where their data is something the release cannot serve; storefronts that retire registry listings they no longer hold; one vocabulary — a role is an actor, a stateful process is a service.

**Non-Goals:** business-schema redesign; automatic downgrade; the registry's PostgreSQL cutover and its rollout Job; adopting Alembic for the in-house services; option-ID stability across a release that changes the option envelope.

## Decisions

### D1 — Every stateful service is in scope

The VM storefront, the bare-metal storefront, the API-credit storefront, the API-credit service, and the registry converge on one mechanism, with compute provisioning brought onto it as well. The three storefronts share one construction path, so bare metal cannot be left out; the API-credit service's guard already exists, and its in-process exception is removed; the registry's command, guard and deployment phase over its existing Alembic machinery are small and make this change the real head of the registry campaign.

Rejected: the proposal's VM-and-API-credit scope (bare metal would need a second, opt-in migrating path in core); storefronts only (keeps a named exception and a crash-loop failure mode); leaving the registry with `migrate-registry-to-postgres` (its dependents would conform to conventions never set for it).

### D2 — One in-house migration engine in a foundation kit; the registry stays on Alembic behind the same contract

A new market-neutral foundation kit holds the engine: the `Migration` type, a `Chain` (its service, command, migrations, v0.3.0 floor IDs and baseline IDs), `migrate` (which adopts at the floor), `check` (returning *absent*, *behind*, *ahead*, *unsupported*, or *compatible* with the differing IDs), a refusal-message renderer that does not depend on the engine, and `schema_snapshot` for tests. It runs over a small adapter per connection type (`sqlite3` and SQLAlchemy). Provisioning, the API-credit service, the three storefronts, and every kit that owns tables use it; `kit/site`, present in both the provisioning and API-credit databases, contributes its migrations once to both chains. Provisioning's migrations take a connection rather than an `Engine`, so every migration commits with its record. The registry keeps Alembic — its PostgreSQL path — and returns the same result and message.

The operator-facing contract — command name, check results, message, deployment phase — does not depend on the engine, so a later adoption of Alembic replaces only the kit's engine.

Rejected: standardizing the contract only (engines already disagree on atomic recording and nothing would make them converge); Alembic everywhere (three to four times the engine work from a baseline, Alembic and SQLAlchemy in every storefront-side kit, and its decisive advantage — portability between databases — unused while these services stay single-writer SQLite; see Open Questions); copying provisioning's engine per service.

### D3 — A clean sweep to a v0.3.0 baseline

Every in-house chain's history is replaced by baseline migrations, one per package whose tables the database's startup builds (core storefront, each such kit, each domain storefront, provisioning, the API-credit service), whose bodies are fixed DDL reproducing the schema dev `9fffe41e9` — the v0.3.0 release's service code — builds when it starts on a fresh database, without opening its stores. They are not `create_all` from current models, which would change silently with every model edit. A committed fixture generated by starting that code proves the baselines reproduce it. The registry's eighteen revisions squash into one Alembic baseline revision, written in Alembic operations, adopted at revision `018_listing_resource_column`.

A database whose `schema_migrations` records every ID the v0.3.0 chain recorded is adopted: in one transaction the command checks the floor IDs, deletes them, and records the baseline IDs, without running the baselines. Recorded IDs prove the storefront constructor's chain ran, and with it the bootstrap that precedes the chain; they do not prove what v0.3.0 created outside the chain — the domain indexes the constructor creates after it, which a crash between the two leaves missing, and the tables stores create when they open, some only lazily (`kit/deal-servicing`'s journal tables first appear when a deal's delivery is registered, so a storefront that never delivered one lacks them). That DDL is therefore not in the baselines: one ordinary migration after the baseline creates every store-open table (D9) and those domain indexes with `IF NOT EXISTS`, the only migration that tolerates objects already present, since a v0.3.0 database may or may not hold them; on a fresh database it simply creates them. Adoption stays on IDs alone, with no schema inspection (13 F4). Migrations merged after `9fffe41e9` — the `20261106` storefront and provisioning migrations among them — stay as ordinary entries after the baseline, and so do migrations later changes add. Any other non-empty database is refused as unsupported, directing the operator to a fresh database.

Supported from the floor: the VM storefront, the bare-metal storefront, compute provisioning, and the registry. The API-credit storefront and service are swept without an adoption path: their baselines are their schema when this lands, and any existing API-credit database is refused.

Deleted with the sweep: core's unversioned bootstrap, every pre-floor migration body, the two-pass application and the `required_tables` skip, the identity and legacy context hooks, the per-migration tests, and DEPLOYMENT_AND_CONFIG's notes on individual old migrations. One ordinary migration after the baseline drops the frozen tables (VM's `compute_allocations`, `resources`, `hosts`, `resource_transition_events`, `compute_pool_members`, and `compute_capacity_pools` or `compute_inventory_pools`; bare metal's `bare_metal_accepted_site_generations`), whose extraction purpose applied only to pre-floor databases; the rule that the engine skips recorded IDs it no longer lists is retired with them. `market-storefront migrate-storefront-domains`, its tests, and the requirement "Legacy storefront domain migration is transactional" are removed: their only input is a pre-floor database.

Planning must confirm that no schema change since the floor reached a database through the unversioned path (`_ensure_domain_tables`, `create_all`); any that did becomes a migration after the baseline, or a v0.3.0 database would adopt without it. The same audit covers the window before the floor: a bootstrap change made after the last migration ID the v0.3.0 chain added, with no ID of its own, would leave a database recording every floor ID without it — a column missing from a table that exists, which the store-open migration's `IF NOT EXISTS` cannot repair — and any such change also becomes a migration after the baseline.

Planning ran that audit at `7091c186c` and found nothing to add. Since the floor, the one commit changing schema code (`7091c186c`) adds only versioned migrations: VM's `20261106_001`/`_002`, bare metal's `-0016-`, provisioning's `20261106_002_reservation_placement_key`, the API-credit service's `20261106_008`, and `kit/site`'s placement-key columns, which those migrations add to existing databases. Before the floor, all three storefront chains last gained an ID in `3c0edcc40` (2026-10-28, settlement-runtime and contact-exchange migrations every storefront composes), and the only schema code changed after it, in `38a5fec12`, creates new tables at store open — deal-servicing's and bare metal's lifecycle cursor — which the store-open migration covers; provisioning last gained an ID in `9623f99e9` (2026-11-06), and the one later commit to its schema files, `5839fb201`, changes job parameters, which are stored as JSON, not schema. The registry has no unversioned path beyond its blank-database bootstrap. An implementer who finds otherwise adds the migration and records it in the section's notes.

Rejected for 13 F4: an adoption-time structural comparison with the floor fixture that creates absent store-open tables and refuses any other difference (inspection machinery and a declared store-open set for what a recorded repair migration does through D3's own rule); making the store-open baselines idempotent and running them at adoption (misses the constructor's indexes); refusing any database whose schema differs from the floor (strands every quiet storefront that never delivered a deal).

Correction at closeout (documentation compliance): at the floor no storefront creates an index after its chain — core's `_ensure_domain_indexes` was empty, VM and bare metal did not override it, and API credits' override held only its refusal checks — so "the domain indexes the constructor creates after it" names nothing the floor builds. Each store-open migration creates deal servicing's tables and indexes and bare metal's lifecycle cursor; the `deployment-state` requirement's clause on objects created "after the chain in the storefront's constructor" holds vacuously. The permanent documents describe the store-open migration by what it creates.

The floor is a one-time decision for v0.3.0. Whether a later release becomes a new floor is weighed each time an official release is promoted (D16's RELEASING.md step).

Rejected: ordered bootstrap steps carrying the history verbatim (keeps every older database upgradeable, which the owner does not need); one entry per ad hoc step (more names, same behaviour); leaving the bootstrap outside the chain (invisible to the check).

### D4 — No migration reads operational configuration

Every migration takes only its database. The one migration that needed configuration — the principal migration — is pre-floor and deleted by D3, so the rule compute provisioning already kept now holds for every service, and each migration command reads only its database location and log level.

Rejected: passing configuration to the storefront migration command, or the principal and storefront URL as arguments — both moot once the migration is gone.

### D5 — Compatibility is the exact set of recorded migrations

The startup check compares the recorded IDs with the chain. Fewer is *behind* (listing what is pending), extras are *ahead* (listing the unknown IDs, and any pending ones too: an unknown ID takes precedence, since this image cannot vouch for the database and the remedy is the backup or the image that wrote it, not a fresh database — 13 F5), a database recording some but not all floor IDs is *unsupported*, a v0.3.0 database not yet adopted is *behind* with the adoption pending, no file or no records is *absent*, and only equality is *compatible*. The migration command refuses an ahead database and applies nothing, since applying pending migrations over unknown ones deepens the divergence. The registry's equivalent compares `alembic_version` with the script head. The check opens the database read-only, so it never creates an empty file. An image rolled back over a migrated database is refused; recovery is restoring the pre-upgrade backup or rolling forward, as DEPLOYMENT_AND_CONFIG already prescribes. Shape is enforced by tests, not at startup: a fresh chain must reproduce the floor fixture plus the later migrations, and opening every store on a migrated database must leave the schema unchanged.

Correction at closeout (documentation compliance): "no file or no records is *absent*" is looser than the engine. *Absent* is no file, or a database holding no table but at most an empty ledger; a database holding tables with no ledger, or with a ledger recording nothing, is *unsupported*, which the requirement's "refuse any other non-empty database" already says. The permanent documents state the engine's rule. Since `49 F2`, a *behind* result awaiting adoption names the baseline IDs adoption will record (`adopting`), so the refusal and `--check` name both the floor and the baseline.

Rejected: provisioning's last-ID check (an older image silently serves a database a newer release changed); tolerating declared-additive unknown migrations (needs a ledger column and a flag every author must get right); a runtime shape check (SQLite-specific, and nothing runs DDL outside a chain after D3 and D9); classifying a database both missing and carrying unknown IDs as *unsupported* (its remedy, a fresh database, would point the operator at discarding data they may keep) or as a separate *diverged* result (a sixth public state with ahead's remedy).

### D6 — One console script per service

`market-storefront-migrate`, `bare-metal-storefront-migrate`, `apicredits-storefront-migrate`, `apicredits-service-migrate`, `registry-migrate`, and the existing `compute-provisioning-migrate`. The API-credit service and the registry gain their first console scripts. This follows provisioning's form; a verb on each CLI was rejected because the API-credit service and the registry have no CLI.

### D7 — The deployment phase is an init container under Helm and the command before the application under Compose

The `storefront` chart (per agent), the `bare-metal-storefront` chart, and the `registry` chart gain a `migrate` init container from the application's image with the application's environment, configuration mounts and data volume; the storefront's runs without `entrypoint.sh`, which only starts ZeroTier. Both storefront render tests change from "no init container" to "exactly one, the migration", and DEPLOYMENT_AND_CONFIG's statement that provisioning's migration is the only init container a chart runs changes with them. Under Compose every service, the API-credit services included, runs `sh -c "<service>-migrate && exec <service command>"`, provisioning's existing form. A separate one-shot Compose service was rejected to keep the one form that already exists.

### D8 — Provisioning's own gaps are fixed where the standard is defined

Provisioning moves onto the kit engine with atomic recording (D2), loses its `create_all` calls to its baseline (D3), gains the exact-set check (D5), names its real command in its refusal, and gains the render test its init container lacks: present, from the application's image, with the same database path, ahead of the application.

### D9 — DDL outside a chain moves into the baselines

`kit/deal-servicing`'s tables, VM's delivery records, and bare metal's lifecycle cursor are created by the store-open migration after the baseline (D3), and the `create_schema` calls at store open are removed. A test asserts that opening every store leaves the schema unchanged, which catches the next one.

The refusal checks the storefront constructor runs after its chain go the same way as the rest of its DDL. Bare metal's check that `bare_metal_settlement_records.evidence_json` and `bare_metal_fulfillment_lifecycle.settlement_ref` exist is removed: its baseline creates those columns, and the exact-set check refuses any database that did not run it. API credits' refusal of a listing with no durable binding concerns data, not schema, and stays as a startup refusal, run after the check passes.

### D10 — The API-credit service seeds its `default` pool at startup

ARCHITECTURE.md lets a migration seed only rows a schema constraint requires, and provisioning's migration creates no pool. The service's startup inserts the `default` pool if absent, after the check passes; `_require_valid_pool_declarations` stays as a startup refusal. Keeping the row in the baseline was rejected: no constraint requires it.

### D11 — Each service's Makefile has a `migrate` target

It runs the service's command, as provisioning's does. The proposal's "reinit targets" are dropped: `reinit` refreshes environments in this repository.

### D12 — The requirements change shape

`deployment-state`'s "Service-owned migration history" is modified to cover every stateful service, the exact-set check, and configuration-free migration, and loses its API-credit in-process exception. Added beside it: one mechanism with its command, `--check`, and phase; the baseline and adoption; atomic recording; no schema change outside a chain; composition-owned ordering. "A deployment does not wait on a service's dependencies" is modified so a chart's only init container is the service's own migration. "Legacy storefront domain migration is transactional" is removed. `storefront-publication` and `physical-provisioning` change as D15 records. Requirements governing a migration compute provisioning's v0.3.0 floor already ran are removed with its body (32 F1): `fulfillment`'s legacy-lease cutover, `physical-provisioning`'s host-identity and active-fulfillment migrations, and `site-capacity`'s retired-state conversion, whose API-credit service copy goes with that service's pre-floor chain, since no existing API-credit database is migrated; `site-capacity`'s "Capacity schema separation" is restated under a new name without its migration scenario, and `fulfillment`'s dependency boundary admits the migration kit. Likewise for the registry's floor (49 F1): `registry-discovery`'s "Publisher identity migration preserves ownership", which governs `016_marketplace_principal_auth`, is removed, and "Stable publisher-chosen listing identity" keeps only rotation's preservation of identifiers. Likewise for the storefronts' floor (56 F1), whose identity conversion is deleted with core storefront's pre-floor chain: `storefront-publication`'s "Storefront identity state migrates atomically" is removed; `negotiation-protocol`'s "Negotiation identity migration and recovery are deterministic" is removed and its recovery rule restated as "Negotiation recovery is deterministic"; and `deployment-state`'s "Identity migrations are coordinated and fail closed" is removed and restated as "Identity cutover is coordinated and fails closed", without its rule that each service migrates identity rows or its conflicting-owners scenario, keeping buyer run-log migration, the refusal of old schema and signatures, and the quiesced cutover. Likewise at closeout, on the owner's direction: `physical-provisioning`'s "A bare-metal storefront refuses state written under a retired listing kind" is removed; requirements whose remaining rule still holds are removed and restated without their floor migrations — `resource-pool-management`'s "Explicit valid host membership", "Pool-declared offering modes", "Complete emission and upgrade derivation", and "VM provider identity is namespaced" as "Explicit valid host placement", "Pool-declared deliverable offering modes", "Complete emission of advertisement and backing tags", and "VM provider registration is namespaced"; `site-capacity`'s "Requested offering mode is explicit and bounded by the pool", "A reservation's release handle has one name", and "A lease records when it was activated" as "Requested offering mode is required and bounded by the pool", "A reservation's release handle has a single name", and "A lease records its activation instant"; `physical-provisioning`'s "Host inventory is connection identity", "Host writes declare no capacity", and "A host record describes no hardware" as "Host inventory is connection identity, not capacity", "Host writes create no capacity declaration", and "A host record carries no hardware description"; and `storefront-publication`'s "Storefront holds no physical-resource authority" as "Storefront holds no physical-resource authority or inventory", which drops its retained-rows rules for the VM storefront's drop of the retired inventory tables.

### D13 — Effects on other changes

This change supersedes `hollow-pre-floor-provisioning-migrations`: its floor and hollowing are replaced by D3, and the "long-term policy for retiring applied migrations" it deferred is D3 together with the release-time weighing. Closeout removes its directory and reconciles its row. `migrate-registry-to-postgres` no longer owns the registry's command, guard, or blank-database baseline; it keeps PostgreSQL, the cutover, the rollout Job and the Secrets, and closeout amends its proposal. `store-registry-listings-as-published` adds its registry migration after the baseline revision. `separate-marketplace-registry`'s tasks expect a registry migration resource a disabled registry must not render, which D7 creates — the dependency its index note questions is real, for its design review to record. `multi-domain-storefront-composition` (in closeout) adds "Storefront domain-binding migration is transactional and explicit" for the command D3 removes; whichever change archives second reconciles — this change's REMOVED delta then also covers that requirement, or that change's delta drops it. Changes still in flight that add migrations, `relay-vm-access-without-a-dashboard` among them, place them after the baseline.

### D14 — Every migration command has a check mode

`<service>-migrate --check` reports the check's result and the pending and unknown IDs, changes nothing, and exits successfully only for a compatible database, so an operator sees what an upgrade will apply and can verify a restored backup.

### D15 — Supported databases are repaired, and storefronts retire listings they do not hold

**15a — `ssh` connections.** `physical-provisioning` refuses a stored connection at a version no codec serves and forbade any rewrite but a submission. The v0.3.0 chain wrote legacy hosts at version 1, which v0.3.0 refuses, so every job dispatched to such a host fails before any playbook runs until an operator resubmits the host at version 2. Only the `hosts` row stores a connection: a job reads its host's when it is dispatched (`HostLookup`), and no job record, parameter, or envelope carries a copy. A migration after the baseline rewrites every host's `ssh` version-1 connection to version 2 with the same public fields and protected values — an exact mapping, since version 2 is version 1 with an optional `public_port` that falls back to the connection port — so no job dispatched after the upgrade fails on one, a job queued before it included. A connection whose fields the version-2 codec refuses fails the migration naming its host, and nothing is rewritten. The requirement is modified: no reader upgrades a stored connection, and only a submission stating the version or a recorded migration with an exact mapping rewrites one. `ConnectionSubmission.version` loses its default of 1 and becomes required, so an unversioned submission is refused as missing the field; this changes the host contract, a minor version under the pre-1.0 policy.

The migration does not recover a reservation whose teardown already failed on a version-1 connection. A fulfillment's teardown is one job, identified by its reservation and operation, and an operator's retry-release re-observes that failed job rather than running a second (`physical-provisioning`, "Lease release and fulfillment teardown have separate retry ownership"; its architecture companion's "Proof-driven release" states the limit). That teardown failed before anything ran, so the deal's guest or tenant account is still on the host, and force-release returns the capacity without touching the host. The operator handbook's upgrade procedure therefore has the operator, for each lease `release_failed` at the upgrade, read its teardown job's error, remove from the host whatever the domain's teardown would have removed, and then force-release with a reason and evidence; a create that failed on a version-1 host never ran either, so its compensating teardown left nothing on the host and is force-released after the check alone. Re-running a teardown that failed before its executor ran, under a new job identity, would recover these without manual work; it changes the rule that one fulfillment's teardown is one job for every failure, not only this one, and is recorded as an unowned gap in `docs/development/ROADMAP.md`'s Goal 1.

Rejected: keeping the rule and leaving operators to resubmit every host by hand (the exact mapping does it once, for every host); letting retry-release re-run any terminally failed teardown, or only one that failed before its executor ran, through a new job identity per attempt (each changes the fulfillment-wide one-teardown-one-job rule and the job engine's identity contract, and needs a design of its own); the handbook procedure without the manual teardown step (force-release would return capacity while the previous tenant's workload still runs on the host).

**15b — retiring registry listings.** `storefront-publication`'s convergence requirement already resends what a registry missed for every listing with a publication record at a configured registry. It cannot see a listing without one: a lost record, one from before publication records, or one at a registry whose URL is no longer configured. Each publication pass of all three storefronts therefore lists, at each reachable configured registry, the open listings under the storefront's own publisher principal for the offering modes it serves, and closes each one it does not hold open. Scoping by offering mode lets the VM and bare-metal storefronts share a principal. A preview pass reports without closing; an unreachable registry is swept later. It lives in `kit/capacity-publication`'s runtime, so all three storefronts share it. No wire changes: the list-by-publisher and status-update routes exist. The cross-registry client's `list_listings` merges every registry's results by listing ID and the single-registry query returns one page, so the sweep reads through a new per-registry operation on the cross-registry client, beside its per-registry writes and `get_descriptors`: for each configured registry it pages the publisher's open listings to completion and returns them, or an unreachable result when the registry fails on any page. The sweep reads every page of a registry before closing anything there — closing while paging by offset would shift later pages — and closes through the existing per-registry update; a listing held open locally, including one held while its site's projection is unavailable, is never closed (13 F2). Rejected for 13 F2: each composition building individual registry clients (duplicates fan-out and failure handling above the shared runtime). Rejected: a bare-metal-only fix (the other storefronts close through the same runtime); recording it as an unowned gap (it would leave unfixed a defect a real upgrade hit, while its fix is understood and small beside this change).

**15c — option IDs and shapes.** The option envelope is a forward-only wire boundary (`deployment-state/architecture.md`): an option's ID is not stable across a release that changes the envelope, buyers re-read listings after such an upgrade, and a closed historical registry listing in an older shape stays as history. The operator handbook's upgrade procedure says so; no migration rewrites them.

### D16 — A role is an actor; a stateful process is a service

The permanent documents use *role* for actors — buyer, seller, operator — and *service* for a deployable process with its own state. This change writes its own text that way and updates the permanent documents' uses of "role" for a service for consistency, recording the term in ARCHITECTURE.md's Terms. Where a requirement's name or text changes, the change carries it as a delta.

The selected migration mechanism is guidance for operators and maintainers, not a cross-system principle: DEPLOYMENT_AND_CONFIG.md describes it, RELEASING.md gains the step of weighing a new floor when an official release is promoted, and the `deployment-state` specification and its architecture companion describe it normatively and conceptually.

### Implementation cadence

Two rounds, each reviewed before the next, then closeout.

- **Round 1 — upgrade repairs, the engine, and the reference service.** Two sessions: (a) the `ssh` connection migration and the required `version` (D15a), and the registry-listing sweep with the cross-registry client's per-registry read (D15b); (b) the engine kit and compute provisioning on it — its baseline and adoption, exact-set check, atomic recording, `--check`, corrected message, init-container render test, and `make migrate` (D2, D3, D5, D8, D11, D14).
- **Round 2 — the storefronts, the API-credit service, and the registry.** Two sessions: (a) the chains — baselines in core, the kits and the domains, each composition's chain, the store-open migration, the frozen-table drop, removing `migrate-storefront-domains`, and the store-open tests (D3, D9); (b) commands, checks and deployment surfaces for the three storefronts and the API-credit service — the `default` pool seeded at startup, both storefront charts' init containers and render tests, Compose, Make — and the registry's Alembic squash and adoption, `registry-migrate`, check, chart init container, Compose and Make (D6, D7, D10, D11, D14). The vocabulary sweep (D16) is written with the documentation each session touches and completed at closeout.

## Risks / Trade-offs

- **[A baseline differs from what v0.3.0 builds]** → The committed fixture generated from `9fffe41e9`'s code and the `schema_snapshot` comparison fail the build on any difference.
- **[A post-floor schema change arrived through the unversioned path]** → Planning audits the commits since the floor; any such change becomes a migration after the baseline.
- **[Adoption by recorded IDs admits data the release cannot serve]** → Known defects are repaired by migrations after the baseline (D15a); the floor's own chain is the one place such data is known to originate.
- **[Adoption by recorded IDs admits a schema missing what v0.3.0 created outside its chain]** → The store-open migration after the baseline creates those tables and indexes where absent (D3); a column missing from an existing table is ruled out by planning's audit of the window before the floor.
- **[The engine is retired when services move to PostgreSQL]** → The contract is engine-independent; only the kit's engine is replaced.
- **[An image rollback is refused]** → Intended: recovery is the pre-upgrade backup or rolling forward, which the operator handbook states with `--check` before migrating.
- **[Two storefronts under one principal serving one offering mode would close each other's listings]** → Already an unsupported topology; the sweep's scope is principal and offering mode.

## Migration Plan

An operator upgrading a supported deployment takes a database backup, runs `<service>-migrate --check` from the new image to see what will apply, then deploys; the init container (or Compose's command) adopts the v0.3.0 database and applies the later migrations, including the store-open tables and indexes, the `ssh` connection repair, and the frozen-table drop, before the application starts. For each compute provisioning lease already `release_failed` on a version-1 host, the operator removes from the host what its teardown would have removed, then force-releases it (D15a). A database from before v0.3.0, or any existing API-credit database, is refused as unsupported and the service starts from a fresh database. Rollback past a migration restores the backup.

## Open Questions

- **Adopting Alembic for the in-house services.** Deferred: provisioning, the storefronts, and the API-credit service are expected to move to PostgreSQL eventually, where Alembic's portability matters, but not for a month or two. ## Implementation record

Decisions and findings made while implementing the plan, with their reasons, that D1–D16 do not state. `tasks.md` records what each section built and the evidence for it.

### Floor fixtures

**Generated from the release's published wheels.** On the owner's direction, every floor fixture — provisioning's, the three storefronts', the registry's — is generated by installing the v0.3.0 release's published PyPI wheels in an environment constrained to the release lock at `9fffe41e9`, not by building a worktree of that commit, whose dependencies a rebuild may resolve differently. The constraint matters: unconstrained, provisioning's environment resolved SQLAlchemy 2.1.8 against the 2.0.51 the release shipped. The wheels are the release's code: `main` had not moved past the release, and `d595f0c2e`'s tree equals `9fffe41e9`'s. The registry's published wheel carries no Alembic scripts — its build target packaged `src/core_registry` alone, and the release image copied `core/registry/alembic` beside `src/` — so its generator first checked that the installed `db/database.py`, `db/models.py` and `config.py` are byte for byte `9fffe41e9`'s, then placed that commit's `alembic/` where the release's `db/database.py` finds it, three directories above the installed package.

**Generators are not committed.** Each fixture's README states its procedure; a generator's environment is a hundred-odd version constraints, and a fixture is regenerated only to correct it against the same release. A later floor (D16's release step) is produced the same way. The implementation step runs Python only as `uv run pytest`, so each generator ran once under a grant the owner gave for that run.

### The migration engine

**Transactions.** `migrate` reads the database's state, refuses, and adopts in one transaction, in place of an untested guard that re-checked the floor in a second one; a test fails adoption midway and finds the floor records kept. Each migration then runs in its own transaction with its record. The SQLite adapter ends its transactions with explicit `COMMIT` and `ROLLBACK` statements, since under `autocommit=True` the driver's `commit()` does nothing; the failure tests run under default transaction control, `isolation_level=None`, `autocommit=True` and SQLAlchemy.

**Classification.** A database records the chain once it records any baseline ID, and an ID the chain does not list then makes it *ahead*. A database recording no baseline but every floor ID is *behind* with adoption pending, and any other ID beside the floor makes it *ahead*. D5's closeout correction states the boundary between *absent* and *unsupported*.

**The ledger.** The ledger is `schema_migrations`, and the engine reads and writes only its `id`, so the ledgers provisioning's and the storefronts' earlier engines created (with `applied_at`) serve as they are; `schema_snapshot` leaves the ledger out.

**Foreign keys.** A migration cannot turn `PRAGMA foreign_keys` off, since it runs inside the engine's transaction, where SQLite ignores the pragma; a later table rebuild must work with enforcement as the connection has it.

**Read-only checks.** `check_engine` reads a file-backed SQLite URL through a read-only `sqlite3` connection of its own, and any other engine, in-memory included, through the engine. A URI-form SQLite URL (`sqlite:///file:...?uri=true`) is checked as a plain path; supporting it was declined, since no service configures one.

**What `schema_snapshot` sees.** It sees `AUTOINCREMENT`, which v0.3.0 storefront tables use, `STRICT`, `WITHOUT ROWID`, and an expression index's definition; it does not see a column's `COLLATE`, as its docstring says. Trigger and `CHECK` text are compared after whitespace normalisation, so a baseline may reflow a floor trigger but not change a token. It reads `PRAGMA table_list`, so it needs SQLite 3.37 or later.

**Python version.** The kit declares `requires-python >=3.10`, as wide as the settlement runtime, whose lock could not otherwise resolve it; its code uses nothing newer, though its suite runs only on 3.13.

**Publishing.** The kit is published from its first release, because `kit/site` and the provisioning service, both published, depend on it. Publishing also needs a PyPI trusted publisher and the `pypi-arkhai-kit-schema-migrations` environment (`docs/development/RELEASING.md`, "One-time setup"), which are configured outside the repository; until they exist, the package's publish job fails on `main`.

### Chains and adoption

**A deployment that ran this branch's provisioning chain.** It records every floor ID plus `20261106_002` and `20261108_001`, so it is adopted with nothing pending.

**No table-existence guards after a baseline.** Every migration after a baseline runs on a database the baselines built or an adopted floor, so the post-floor bodies lost the guards they had.

**Baseline DDL.** Each baseline writes a column the floor added by `ALTER` into its `CREATE TABLE` in stored column order, so its snapshot matches the floor's.

**Replaying a fixture's DDL.** SQLite records `CREATE TABLE sqlite_sequence(name,seq)` for an `AUTOINCREMENT` key and refuses to create that table by name, so `tests/floor_database.py` (VM, bare metal) strips that line before `executescript` replays `ddl.sql`.

**API credits has no store-open migration.** Its storefront composes no deal servicing and adopts no database, so its baselines hold every table it opens.

### The `ssh` connection repair

**The return to design.** Section 1 returned the change to design when it found retry-release cannot re-run a teardown whose job failed on a version-1 host: a fulfillment's teardown is one job under `<reservation>:teardown` (`compute_provisioning/job_fulfillment.py`), and the job engine answers a repeated identity with the existing job whatever its status (`jobs/engine.py`, `_repeat`). The design took the option of narrowing D15a to the hosts; the evidence, the options weighed, and the work then in progress are in the return's commit `615d071ec`.

**The literal version 2.** The migration writes version 2, not the codec's currently served version, so a later codec version makes the migration fail rather than stamp a version it never mapped under an already recorded migration.

**The service's patch bump.** The provisioning service took a patch (0.24.1), although an unversioned submission's refusal moved from 400 to 422: the contract change is the contracts distribution's minor bump (0.14.0), and the service's wire routes are unchanged.

### Retiring registry listings

**Each storefront sweeps only the modes it publishes.** The VM storefront sweeps `vm` alone, the only mode its loop publishes, even where its domain registry composes bare metal; sweeping every composed mode would close the dedicated bare-metal storefront's listings under a shared principal.

**The held set is read after the registries.** A listing is recorded locally before any registry is told of it, so reading the held set second never misses a listing the registries already show.

**Closes are not recorded as publications.** A failed close is found again by the next sweep.

**Known limit: a listing stating no `offering_mode` is never swept.** Under a principal storefronts of different modes may share, nothing says whose it is. Listings published before the offering mode was written into the listing resource would be such listings; the upgrade defect D15b fixes was a bare-metal listing, which states its mode.

**The proof is split by level.** A first version ran the registry application in process in a kit test; TESTING.md's library integration (the library's own database, collaborators injected) does not cover that, and it made a kit depend on a deployed service (ARCHITECTURE.md, "Kit areas"), so it was removed. The registry's own integration test proves its paging, the cross-registry client's unit tests its per-registry read, the kit's unit tests the sweep's decisions, and each storefront's tests its wiring against a double. Because the sweep closes only listings whose `listing_resource.offering_mode` it serves, a registry list response that dropped or renamed that field would make it close nothing while every test passed; the round-1 triage (32 F2) accepted the split once the registry's paging test also asserts that field. It declined, as disproportionate, a system scenario that plants an orphaned listing and observes a storefront close it, and an in-process test booting the registry application beside the cross-registry client, which would make a core or storefront package depend on a deployed service.

**Test seams.** The cross-registry client's `client_factory` defaults to `RegistryClient`, resolved when the clients are built, so existing tests that patch the module's name still apply. The API-credit storefront has no injected registry client, so its sweep test replaces the publication service's own `_make_registry_client` on the module that defines it, as TESTING.md's factory-seam convention allows, rather than `build_capacity_runtime` on a module that imports it; it is therefore not application integration. The API-credit sweep logs rather than reports, since its capacity reconciliation keeps no report and its capacity-events preview does not reconcile.

**A function-local import.** `capacity_client.py` keeps one import inside a function: at module level it fails collection with a circular import, since `publication_service` imports `build_capacity_runtime` from it. The reason is stated beside it.

**A declined correction.** The fresh-context check over the round-1 triage fixes questioned the restated "Active fulfillment migration" Reason, which cites `20260713_002`, a migration that by the floor no longer placed hosts in a pool. It was kept: the Reason says "among them" of the migrations that did so historically, and every ID it names is a floor ID.

### Storefront cutover sequencing

**The bootstrap's deletion moved from 6.2 to 7.5.** Removing core's constructor bootstrap changes all three storefronts at once, since each constructs core's `SQLiteClient`: from then on every test that builds a client on a fresh file must migrate it first — about 149 constructions in 66 test files — and the pre-commit hooks run every suite, so the deletion cannot land before section 7 declares the chains. Adding the baselines also gave each table-owning package new public API and a dependency on the engine, and `arkhai-kit-settlement-runtime` was pinned exactly by six packages, so its minor bump reached each of them. The owner chose to commit section 6 with the baselines alone and to do the deletion with 7.1.

**An interim in-process migration.** Between sections 7 and 9 each storefront composition applied its own chain before opening the database, so the storefronts kept starting on fresh databases in the lanes until section 9 replaced each call with the startup check. A refusal raised in that interval names a console script section 9 registers; the gap lasted within one review round.

**Core's client constructor.** It lost its principal and legacy-seller arguments with the principal migration they served, so the VM and API-credit `get_sqlite_client` no longer resolve the signer.

### Migration commands read only their database settings

**Splitting settings loaders.** Each command reads only its database location and log level (D4), so where the application's settings module resolves more at import, the layered loading moved to a `settings_source` module the application's configuration builds on. The API-credit service's `config.py` reads the admin-key file at import and refuses an unreadable one, so a command importing it could not run — `--check` on a restored backup included — without the application's secret mounted. The VM and API-credit storefronts' `utils/config.py` resolve chains, the agent ID and VM's base URL (through ZeroTier) at import. The registry's `settings_source.py` gives `DatabaseSettings` and `load_database_settings`, and `core_registry.db`'s `__init__` stopped importing `db.database`, whose engine reads the application's settings. Bare metal's `config.settings_source()` already only read; its configuration states no log level, so its command logs at INFO. Provisioning's command imports its full settings, whose loader reads no secret file at import.

**An empty `db_path` is refused.** Unset or empty, it would have migrated a file named `None` or a temporary database.

**No `--config` option on the storefront commands.** `--config` reaches `storefront_config_file()` alone, while the settings `serve` reads its `db_path` from come from `storefront_config_files()`, which ignores it, so `serve` and the command already read the same database.

**Seams left as they are.** `migrate.main` takes `argv`, since pytest's own arguments would otherwise reach its parser. The provisioning command's tests set the settings source through the service's own loader, as the existing configuration test did; passing `migrate.main` its settings would be the cleaner seam. The commands' `main` functions are near-identical copies across provisioning, the API-credit service and the storefronts, as are the storefronts' check helpers; moving them into a shared helper in the engine kit is reasonable and was left for review to weigh.

### Deployment surfaces

**Images install their own wheel.** The API-credit service's and the registry's images now install the project's wheel (`scripts/uv_project.py install-wheel`), as the provisioning and storefront images did, since an image that runs copied source installs no console script.

**Bare metal's Compose form sets `entrypoint`.** Its image's entrypoint is the CLI, so the migration-then-serve line replaces the entrypoint; that drops the image's `serve` command, which the line restates.

**Which images migrate in their default command.** The storefront images' default commands are unchanged: Helm runs the migration as an init container and Compose states its command. The API-credit service's and the registry's images migrate first in their `CMD`, the Compose form; so the registry chart's application container states its own `uvicorn` command, and under Helm the migration runs once, in the init container.

**Render tests read the application container.** The init container's `env` and `volumeMounts` come first in each Deployment, so the tests and helpers that read the first container's (the storefront payments-check tests, bare metal's environment and command helpers, `test_release_topology.py`'s `_resolver_environment`) now select the application container.

**Unrun local checks.** The local Compose bring-ups, `make migrate` and a `docker run` of the image's command were denied in the implementation sessions. Tasks 8.2 and 9.3 stayed checked rather than unchecked, their pending evidence being the lanes that start each service through these commands on fresh volumes; validation 37 at `6ec41c9fc` passed.

### The registry on Alembic

**The return to planning.** Before any of section 10 was implemented, its session found that the registry's published wheel carries no Alembic scripts and its image installs only the lock's dependencies (`--no-install-project`), serving from copied source with `--app-dir /app/src`, so `registry-migrate` needs the scripts packaged and the wheel installed — touching the registry's `Dockerfile`, `pyproject.toml`, `alembic.ini`, `env.py` (whose `sys.path` insertion assumed the source layout) and version, none of which the plan named — and that the floor generator needs the owner's grant. The replan split the section into the fixture, the packaging, the squash, the command and check, and the deployment surfaces.

**Adoption rewrites `alembic_version`.** Alembic cannot locate a deleted revision, so adoption is an `UPDATE` of `alembic_version` from the floor to the baseline in one transaction before upgrading; it fails with nothing changed, as a `MigrationFailed` the command reports, if the row changed since the check.

**Squashed revisions are unsupported, not ahead.** `PRE_FLOOR_REVISIONS` lists the seventeen squashed revisions before the floor, so a database at one is refused as unsupported naming what it lacks rather than as ahead.

**One revision at a time.** The command upgrades one revision at a time, so a failure names the revision that failed rather than every pending one.

**Known limit: SQLite DDL under Alembic is not transactional.** A fresh migration failing partway leaves `alembic_version` with no row beside the tables it made; the check reports that database unsupported, and it is replaced by a fresh database, as the fresh database it was.

**One head.** A later revision follows `v0_3_0_baseline`; the script must keep a single head for `classify` to report pending revisions.

**The filter specification moved into the package.** The default filter specification resolved three directories above `api/filter_spec.py`, which in an installed wheel is the environment's `lib/`, not `/app`, and every Compose compute registry relies on that default; it now resolves beside the code.

**Test seams.** The lifespan test replaces its settings object's URL rather than taking an injected seam: `lifespan` reads the module's settings and has no seam, and the suite's conftest already replaces the authority on that object; the test's note calls it what it is, not application integration. Behind at a known earlier revision is proven only at unit level, since the script holds the baseline alone.

**Declined refusal wordings (49 F2).** The fresh-context check over 49 F2's fix declined, as outside the finding, the kit's existing "migrations X are pending" for a single ID, and an in-house adoption refusal naming a current migration: the in-house floor has no single revision, and the scenario requiring both revisions is the registry's.

### Test placement and levels

**Tests opening a real database are integration tests.** Where the plan said "unit", a test that opens a real SQLite file went to `tests/integration/`, as TESTING.md's library-package rule places it: the engine kit's engine and snapshot tests, the storefront kits' baseline tests, deal servicing's schema test, and the tests moved in provisioning, core storefront, the settlement runtime and the VM storefront. A service's migration suite with no application is named library integration, though TESTING.md defines that level for kit libraries; closeout's "Migration Tests" section says so.

**Not moved: the VM storefront's other unit modules that open a real database** (`test_publications.py`, `test_negotiation_thread.py`, `test_settlement_composition.py` among them). TESTING.md's move-when-touched rule is written for library packages, those modules opened real databases before this change, and the touch was one migrate call each; the rewritten `test_migrations.py` did move.

**Deleted tests were judged one by one.** A test whose subject was a deleted migration or legacy converter was deleted; a live test in the same module was kept on a migrated database. Declined: a service-level test of backfilled fulfillment rows, since the rows the deleted backfill wrote are ordinary fulfillment states, which `test_fulfillment_convergence.py` covers with natively created rows; and kit-level tests of each exported provisioning baseline, since only the provisioning service holds the floor fixture they reproduce and its chain test proves them against it, with every mapped column.

**Bare specification pointers.** New modules' docstrings end with a pointer to `openspec/specs/deployment-state/spec.md` rather than to a heading, because the requirements they mean existed only in the change's delta until archive; closeout's comment check confirms them.

**Concurrent sessions.** Running suites while another session reinstalls the same package's `.venv` (each `test` target's `reinit`) gives spurious import errors; the shared `.dist` wheels are rebuilt only by `make lock` or `make dist`.
