# Active Change Campaigns

This index groups active OpenSpec changes by delivery sequence. It is a planning map, not a normative specification or an umbrella change. Each linked change retains its own acceptance, validation, synchronization, and archive boundary. Capability behavior remains authoritative under [`openspec/specs/`](../specs/README.md).

Each change row has a `Status`, a `Depends on`, and a `Notes` column, governed by `planning-governance`'s index requirements.

`Status` holds exactly one value. The phases, in order, are `design`, `planning`, `implementation`, and `closeout`, and within a phase a change is:

- **`ready for <phase>`** — the previous phase is finished and nothing in the change itself prevents this one starting;
- **`in <phase>`** — the phase has started and is not finished;
- **`blocked in <phase>`** — the phase cannot proceed for a reason that is not another change: an external input, real hardware, protected credentials, or a pending owner decision (`blocked in design` means the design needs an owner decision). `Notes` names the reason.

Outside the grid: **`deferred`** (no work until the activation condition in `Notes` holds) and **`archived`** (closed out — which archives the change under `archive/` — its closeout review's triage advanced it, and the archive cleaned up).

`Depends on` lists every change that must reach `archived` before this one proceeds, each followed by the phase it gates when that is earlier than implementation, e.g. `` `redesign-authenticated-replay-state` (design) ``; an entry naming no phase gates implementation. A dependency on another change never appears in `Status`, and one gating only part of a change goes in `Notes`. When a dependency lands — its closeout review's triage advances it and archive cleanup sets it to `archived` — archive cleanup removes it from each dependent's `Depends on` and sets each dependent that is `ready for planning`, `in planning`, or `ready for implementation` to `ready for design`; an `in implementation` dependent keeps its status, and a `blocked in` one keeps it too and its `Notes` record that design reverification is owed. The dependency graphs below illustrate; the column is authoritative.

A change is ready to start when its status begins `ready for` and none of its listed dependencies gates that phase or an earlier one.

## How this index is organized

Campaigns come in two kinds.

**Roadmap goals** are the directional goals in [`docs/development/ROADMAP.md`](../../docs/development/ROADMAP.md). Those sections carry sequencing and readiness only — why a goal exists, the value it delivers, and what is still true today all live in the roadmap, which is the single place they are maintained.

**Lesser goals** are coherent bodies of work with no roadmap goal behind them. Each gets a short summary, because a reader landing on four registry changes deserves to know what they add up to. A lesser goal is not a smaller roadmap goal: it is work that improves how the system is built without changing what the market can do.

A change appears exactly once, in its primary home. Where a change serves more than one goal, the other goal notes it rather than listing it again.

## Lesser goal — Make the change workflow a tool any repository can adopt

**What it adds up to.** The change workflow is what keeps agent-driven work designed, reviewed, validated, and documented rather than merely implemented. Today it exists only inside this repository. That has three costs. Other repositories cannot use it. Its improvements are entangled with market changes, so it cannot be versioned on its own. And general engineering guidance has no home outside this repository's documents, so another repository would have to restate it. As a separately versioned tool, the workflow gives every adopting repository the same discipline. Shared guidance is maintained once, and this repository's own documents shrink to what is specific to it.

The goal also makes the workflow the easiest way to drive a change, not just the correct one. A change's state lives with whoever is running it, so handing it over or sharing it means passing around records and transcripts. A hosted runner keeps that state in one place. Anyone working on the change can watch it live or take it over, each person using their own credentials.

The goal does not gate merges on the workflow. A patch made directly to `dev` remains legitimate where the workflow's overhead outweighs its value. What the goal provides is visibility into whether a change went through the workflow, not enforcement.

This is a lesser goal because it changes how changes are made, not what the market can do. Unlike other lesser goals it carries a current state and open gaps, as a roadmap goal would, because no roadmap goal holds them. **Current state.** The workflow lives entirely in this repository:

- **Skills:** ten leaf skills under [`.agents/skills/`](../../.agents/skills/), linked into Claude Code's and Codex's project skill directories.
- **Engine:** one package, [`scripts/change_workflow/`](../../scripts/change_workflow/), reached only through one command, [`scripts/change-workflow`](../../scripts/change-workflow); repositories call the command and never import the package.
- **Entry points:** the command, and the make targets of the package's fragment, [`workflow.mk`](../../scripts/change_workflow/workflow.mk), which the root `Makefile` includes as a convenience outside the engine's surface.
- **Contract:** two capabilities, each organized by an index of requirement ids. The [`change-workflow` specification](../specs/change-workflow/spec.md), with its [`index.md`](../specs/change-workflow/index.md) and its [`README.md`](../specs/change-workflow/README.md) and diagrams, describes the workflow and its engine for any adopting repository: the engine's interfaces tiered public, provisional, or internal, one format version for a change's records, compatibility judged by semantic versioning, the graph's vocabulary closed, and the roles an adopting repository provides. [`market-change-workflow`](../specs/market-change-workflow/spec.md) holds this repository's own part — its validation parts, its Helm validation namespace, its workflow values — and how it provides each role, which a test holds complete for the make targets and repository paths the skills, step table, and make fragment name.

The workflow has no version of its own: a change to it ships with whichever commit of this repository carries it, and its proposal names each public interface it changes and whether the change is compatible.

What the workflow assumes about a repository is declared in one file, [`.agents/workflow.toml`](../../.agents/workflow.toml): the repository's hooks, named by when they run, with the workflow's default checks a repository turns off only by name; validation's parts, their order, evidence, and cleanup; the protected branches, the inert paths, each step's models, and the documents each step loads. The branch a change lands on is recorded with its clone and the remote is read from Git. Skills run the hooks through `scripts/change-workflow run`, which holds which step may run each and records every invocation on the run's log line. The engine holds none of this repository's values.

Most skills are written in repository-neutral terms. Some are not:

- **Validation** learns its parts from the engine, but still describes this repository's Helm charts, end-to-end pipeline, per-change validation namespaces, and capacity record where its diagnosis needs them.
- **The closeout task** mixes checks every repository would want, such as comment hygiene and citation resolution, with checks specific to this one, such as packaging and pipeline evidence.

An unattended step is held to an allowlist of commands per step, in [`.claude/change-steps.toml`](../../.claude/change-steps.toml), in Claude Code's rule syntax. The rules that only ran what is now a hook are gone, but the allowlist still grants this repository's make targets and scripts for engineering work. The guarded push is a deny rule the step's session is subject to, not a credential the session lacks.

Unattended steps run headless in Claude Code. Reviews run in Codex's read-only sandbox first, falling back to Claude. No step that writes runs on any other harness.

A change's records are untracked. They live in its clone and in the owner's workspace, and the transcripts of its sessions live on the machine that ran them. Helm validation runs against an explicitly named Kubernetes context.

The guidance agents load is not layered. [`AGENTS.md`](../../AGENTS.md), [`ARCHITECTURE.md`](../../docs/development/ARCHITECTURE.md), [`TESTING.md`](../../docs/development/TESTING.md), [`DEPLOYMENT_AND_CONFIG.md`](../../docs/development/DEPLOYMENT_AND_CONFIG.md), and the [OpenSpec README](../README.md) each mix three kinds of material:

- engineering conventions that would hold in any repository;
- rules of the workflow itself;
- this repository's own architecture and examples.
