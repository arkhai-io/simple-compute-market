## 4. Map projections into commercial inventory

**Resolved (2026-08-03, `design.md`, "Section 4 design"):** the mapping schema already exists — `derived_compute_listings` (and `derived_bare_metal_listings`) — and carries no commercial fields itself; pricing/settlement/policy already live entirely on the generic `listings` table via `listing_id`. Extend, don't replace. Also corrects Section 1's framing: the CLI-derived listing flow and operator/API-driven listing creation are one `create_listing` code path, not two.

- [ ] 4.1 Add `site_id` to `derived_compute_listings`/`derived_bare_metal_listings` and fix `derivation_key` construction (`reconciler.listing_pool_key`/`listing_resource_key`) to include it. **Confirmed real bug, not just hygiene:** today's `derivation_key` is site-blind, so two sites naming a pool identically collide under `ON CONFLICT(derivation_key) DO UPDATE`, letting one site's mapping row silently overwrite another's.
- [ ] 4.2 Backfill unambiguous current rows and quarantine ambiguous or unsupported local physical identities without deleting agreement history. Still open as originally scoped — this task's substance (identity backfill against existing single-site-assumption rows) is unaffected by the schema-reuse finding above.
- [ ] 4.3 Redirect `reconciler.available_compute_slices`' capacity source from live `SELECT ... FROM resources` to the `site_resource_pools`/`site_capacity_buckets` projections (`site_projection_cache.py`), keeping the existing `stale_open_listing_ids`/`closed_available_listing_ids` close/reopen logic — only the availability *source* changes, not the reconciliation mechanism. Decide and record the migration sequencing: parallel-run against both sources before cutover, or direct replacement behind a feature control (`design.md`'s existing Migration Plan step 4 language, not yet resolved to one concrete approach here).
- [ ] 4.4 Add explicit pinned-site routing to `AggregateCapacityClient.reserve()` (`core_storefront/aggregation.py`) and switch VM claim construction to attach the mapped `site_id` for any listing with a known site mapping. **Confirmed real gap, not hypothetical:** `reserve()` has no way today to target one site for a fresh reservation — it always falls through `_placement`'s multi-site trial order, which combined with `pool_id` not being globally unique (task 1.3) means a mapped listing's claim can currently be admitted against a same-named pool on the *wrong* site if placement tries that site first. **Resolved shape (2026-08-03, corrected 2026-08-03 after Section 5's Q3, `design.md`, "Resolved: Option 1, split into private methods"):** `reserve()` gains an optional `site:` parameter and becomes a thin dispatcher over `_reserve_at_site` (exactly one site, no fallback) and `_reserve_by_placement` (today's unchanged fan-out body, only for listings with no site mapping at all). **Corrected condition:** `_reserve_at_site` applies whenever a site mapping exists — fungible or resource-pinned listings alike, not only resource-pinned ones — because the storefront only ever commits to a *site*; which physical resource satisfies the claim is the provisioning service's decision (ledger admission match or fulfillment placement), never the storefront's. `site_id` is not added to `ComputeResource`/`offer_resource` or threaded through `compute_capacity_claim_from_order`'s claim (that model is the public, buyer-negotiated offer); the caller looks it up from `derived_compute_listings` by `listing_id` immediately before calling `reserve(..., site=site_id)`. Add parity diagnostics before removing the old fan-out reader for listings with no site mapping.
- [ ] 4.5 Add the equivalent `site_id`/mapping-table extension for the bare-metal storefront (`derived_bare_metal_listings`, already covered by task 4.1's schema change) and confirm bare-metal's claim-routing path has the same pinned-site gap 4.4 found for VM, without importing bare-metal models into core.
- [ ] 4.6 Prove projections never participate in live admission, assignment, or provider dispatch decisions. **Largely satisfied by construction** (`design.md`): `reserve()` always calls the real site's live endpoint for admission; the mapping/projection layer only selects which site and what claim to send. This task is a regression-proof test (no shortcut "skip live check, trust the last projection" path exists), not new design.
