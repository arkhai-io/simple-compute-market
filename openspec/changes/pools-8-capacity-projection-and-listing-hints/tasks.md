### Implementation plan (planned 2026-08-03)

Grounded against the exact current code, not just the design decision. Confirmed while planning: `ProjectionCache.load()`/`refresh()` (`core/storefront/src/core_storefront/site_projections.py`) already catch every exception internally and set `state=invalid`/`stale` rather than raising — so `site_projection_cache.load_site_projections()`'s `asyncio.gather(caches.resource_pools.load(), caches.capacity_buckets.load())` cannot fail one site and block another from being inserted into `_caches`. Task 2.2 is therefore "add a regression test proving this," not "fix a bug" — worth stating plainly since it would be easy to assume otherwise from the design-phase description alone.

**2.1 — status surface.**
- New function `market_storefront.services.site_projection_cache.projection_status_summary() -> dict[str, dict[str, dict[str, Any]]]`, shape `{site_id: {"resource_pool": {...}, "capacity_bucket": {...}}}`, each leaf built from `ProjectionCache.view()` (`ProjectionCacheView`: `identity`, `value` — presence/absence only, never the value itself, to avoid duplicating the full projection payload into a status endpoint — `state`, `last_error`). Iterate `projection_caches()` (already exported, already returns a copy) rather than reaching into `_caches` directly.
- Wire into `SystemService.get_health(*, include_registry: bool = False)` (`market_storefront/services/system_service.py`) as a new `checks`-adjacent key, e.g. `result["site_projections"] = projection_status_summary()`, gated the same way `resource_count` already is (only under `include_registry=True`, i.e. `/api/v1/system/status`, not the fast `/health` probe) and wrapped in the same try/except-returns-`None`-on-failure pattern already used for `resource_count` immediately above it in that function.
- Explicitly do not add a `_check_is_healthy` rule for this key or fold it into `all_ok` — per Section 2's revised decision, one site's `invalid`/`unavailable` state must not present as global degradation. It's reported, not gated.

**2.2 — poller retry regression test.**

**4.2 -- backfill and quarantine, revised after discussion (2026-08-03) from the originally planned migration-based approach:**
- **Why a migration was the wrong mechanism, found by tracing it through rather than assumed:** the planned approach ("backfill `site_id` from the single configured site when exactly one site is configured") requires knowing the current site count -- but that lives in live deployment config (`market_storefront.utils.config.settings.capacity.sites`), not schema. A migration runs exactly once, ever (recorded in `schema_migrations`, never replayed) -- baking a site-count snapshot into a one-time migration goes stale the instant a second site is ever configured later, with no way to revisit the decision. This is exactly the kind of hard-coded assumption already rejected once in task 4.1's own fallback logic; the same principle applies here.
- **The actual mechanism: task 4.1's read-time `configured_site_count`-gated fallback already solves this, dynamically, on every call** -- no separate backfill step needed. A legacy row with `site_id IS NULL` is handled correctly and consistently by `stale_open_listing_ids`/`open_listing_resource_keys`/`mark_derived_listings_closed`'s existing fallback: exact when exactly one site is configured, quarantined the moment a second one exists, re-evaluated fresh every time rather than fixed at one point in history.
- **Two remaining gaps, function by function, both resolved by direct confirmation rather than assumed:**
  - `closed_available_listing_ids` matches against the *stored* `derivation_key` column directly, so a legacy row's old-format key won't match a freshly-computed new-format one -- a legacy closed listing won't be found as reopenable. **Accepted as fine:** listing derivation is idempotent by design: the storefront creates a new listing for that slice instead. The old row stays orphaned/closed, harmlessly.
  - `load_derived_listing_for_slice` has the same stored-key-matching dependency, used only by `cli_publish.py`'s closed-listing-reopen path (`_reopen_derived_listing_if_present`). **Investigated the actual risk before accepting it:** duplicate *active*-listing avoidance is a separate, already-correct mechanism (`open_listing_resource_keys`, which recomputes fresh with the same dynamic fallback and already filters out any candidate with an existing open listing) -- so a legacy row not being found here only means a missed opportunity to reuse a closed listing's row, never a duplicate open listing. Same "idempotent re-derivation" outcome as above, confirmed rather than assumed.
- **Real bug found and fixed while working through this, not part of the original plan:** demonstrated that `listing_pool_key`/`listing_resource_key`'s naive colon-delimited format is not collision-free -- `site_id` and `pool_id`/`resource_id` are operator-chosen strings with zero character validation anywhere in the codebase (`kit/resource-pools/src/market_resource_pools/pools.py`'s `PoolCreate.id` is a bare `str` field), so `(site_id="a", pool_id="b:c")` and `(site_id="a:b", pool_id="c")` produced an identical key -- verified concretely, not hypothetically: both produced `"pool:a:b:c:gpus:2"`. This is a real risk to the `derivation_key` `UNIQUE` constraint's own correctness (a genuine collision would let `ON CONFLICT DO UPDATE` silently misattribute one pool's mapping row to another), not just a legacy-migration concern. Fixed with a length-prefixed encoding (`f"{len(value)}:{value}"` per field) -- provably injective regardless of field contents, since each field's boundary is fixed by its own explicit length rather than inferred from delimiter scanning. New `TestKeyValidation` tests prove no collision for the demonstrated case, an adversarial "field value looks like a length prefix" case, and a broader sweep of boundary shifts across the same underlying characters.
- No new migration was written; no new task remains here.

FROM resources`". This flow already works correctly today and is out of this task's scope; do not touch it without a separate, explicit decision to do so.
