## Context

The work landed as PR #275, stacked on PR #272, before the change was taken through the current workflow; the change records it, its design review, and the rounds after it. The scenario was run against a configured payments target and passed its three calls; that run is what found the provision-terms serialization defect in the bare-metal buyer.

## Goals / Non-Goals

**Goals:** one connected-system scenario proving a fixed-term bare-metal deal settled through Arkhai payments, from discovery to refund and physical release; a scenario that leaves nothing behind on failure; bare-metal buyer commands that complete an agreed negotiation.

**Non-Goals:** real SSH access and revocation; live payment qualification; any change to settlement design or a new buyer command.

## Decisions

- **D1 — Supply and access reuse the bare-metal deal driver.** `BareMetalComputeDealDriver` seeds backed whole-machine supply and supplies the mock access semantics. A pool override supplies one hourly USD/6 payment option without changing other pools. The scenario's stages stay distinct from the canonical Alkahest compute stages, which bind escrow semantics and cannot represent a payment purchase.
- **D2 — The buyer is configured through the shared payments helper.** It uses the shared serializer under `bare_metal.arkhai_payments`, pins false receipt mode, and generates only a public SSH key for configuration. Registry and seller responses verify against lane-owned pins.
- **D3 — Re-drive recovers the original purchase.** Replay reads the original run's validated references and resolves the run-recorded profile and principal through `BuyerProfileService`, then calls `SyncStorefrontClient.settle_agreement`: it neither buys again nor invents a settle command. Every fulfillment read and the teardown sign as that purchase's buyer; the lane's ordinary buyer fixtures use another signer and cannot read this purchase.
- **D4 — Financial reversal and physical release are separate.** The seller refund calls the pinned seller and checks the payer's transaction snapshot; physical teardown separately follows mock reclaim, the lease release, and whole-host capacity return. Real SSH belongs to the protected lane.
- **D5 — Completion serializes accepted terms through the outcome.** `market bare-metal buy` and `market bare-metal request-introduction` write the accepted provision terms into `run_ended` through the negotiation outcome's serializer, which copies a dictionary and dumps a model. The bare-metal buyer passes the negotiation client no provision-terms decoder, so the terms always arrive as a dictionary, and calling `.model_dump()` on them failed every agreed negotiation. Both commands get unit-level regression tests, since no pipeline scenario drives either to an agreement (01 F5).
- **D6 — A failed run compensates what it started.** Unless the scenario's own refund stage recorded the deal torn down, its module cleanup finds the purchase's negotiation and approved payment in the buyer's run log — which records them as they happen, so they are found even when the purchase command failed or timed out, or a later assertion did — and does nothing more when no payment was approved. Otherwise it reads whether a host was delivered, refunds the payment, and releases a delivered host not yet released. The status route's "not found" (404) means no fulfillment, and so does its 409 for a payment it has not verified with no fulfillment record (a pending receipt, or a refunded deal never delivered); its other 409s describe a host that is reserved or delivered but cannot be read. The route gives no structured reason, so that one 409 is told apart by its signed detail, and every other failure is raised: a changed wording then reports a failed read rather than hiding a host. The read is made before the refund and decides the release, and only a read that failed is repeated after it. Refund and release are idempotent (a repeated refund returns the same result; a repeated teardown returns one operation), so cleanup need not know how far the stages got. The buyer records a payment approved before the seller has verified its receipt, and the seller refuses to refund a payment it has not verified (409) and answers 503 while the payments service is unavailable; those refusals, and a storefront that cannot be reached, are retried for a bounded window of 60 seconds. A 409 can also be final — nothing left to reverse, an invalid receipt — and is then retried the same window before it is reported. A refund that still fails, retried or not, fails the cleanup naming the negotiation and transaction, for an operator to reverse any hold that remains. The decisions live in an e2e helper with the fulfillment read, refund, release, clock, and sleep injected, and the predicates that classify the clients' errors beside them, so each branch is unit-tested; the scenario supplies its real clients. The scenario drives a real payments target, so a failed run would otherwise leave a hold there until its dispute window ends, and a host allocated in the lane (01 F2; 03 F1, 03 F3).
- **D7 — Every cleanup step runs, and the held loops resume last.** Each owned cleanup step — compensation, removing each mock rule, draining, removing the pool override — is attempted on its own, its failure recorded and reported at the end. Each mock rule is deleted by its own step through the provisioning test client: deleting a rule already gone reports it not deleted, so only a real failure raises, and the shared deal driver's removal, which discards every error, is not used (03 F2). Resuming the storefront's lifecycle loops, fulfillment convergence, and the lease watchdog sits in an outer `finally`. That is `docs/development/TESTING.md`'s rule that a module resumes the loops it paused in a finaliser, so a failing stage does not leave them stopped for the next module in the lane (01 F3).
- **D8 — The scenario's contract is its own requirement, delivered by this change's delta.** It was first written as a scenario under `test-compatibility`'s "A deployable domain's deal runs on every end-to-end run", which this scenario does not do: it skips in the pipeline. It is an ADDED requirement beside "External payment qualification names its target", so it does not restate the every-run requirement, and the archive merges it once reviewed (01 F4).

## Evidence boundaries

- **The bare-metal commands are tested with their module's collaborators replaced.** `market bare-metal buy` and `market bare-metal request-introduction` construct their configuration, identity, registry client, negotiation, and settlement transport themselves, so their completion path has no injected seam. Their regression tests replace those names on the command's module, as the bare-metal buyer's composition tests already do, and keep the run log real. That departs from `docs/development/TESTING.md`'s unit-test convention against patching module-level imports; making the commands take injected collaborators would restructure the bare-metal CLI, which this change does not otherwise touch, so the departure is kept and recorded here (D5).

- **The compensation decisions are unit-tested; their composition is not run.** The helper's tests drive each branch against an injected seller and clock: a run log cut off mid-line, no purchase, an unpaid agreement, an undelivered and a delivered purchase, a fulfillment read that failed before the refund and is read again, an already released host, a settled deal, a refund retried until it clears, one still refused after its window, and one that cannot clear; and the predicates mapping the fulfillment read's 404 and its unverified-payment 409 to no host — but not another 409 — and choosing which refund failures are retried. The seller's statuses are modelled, not served: that a pending receipt answers 409 is read from the storefront's code. Wiring them to the real storefront, payments service, and site runs only against a configured payments target, and a failure-injection run of it is not part of this repository's pipeline.

## Risks / Trade-offs

- **[Direct loop pauses]** → the supply fixture pauses the storefront, fulfillment convergence, and the lease watchdog itself. `unbacked-bare-metal-listings` replaces direct pauses with shared module holds and a source check that refuses them, and converts this module with the other bare-metal ones; its index row records that.
- **[Pipeline evidence]** → the pipeline configures no payments target, so the scenario skips there; the configured run is evidence recorded with the change, not a pipeline result.
- **[A cleanup killed by a timeout]** → a finaliser that does not run cannot compensate; a hold then expires with its window, and the lane's stack is recreated by the next run.
