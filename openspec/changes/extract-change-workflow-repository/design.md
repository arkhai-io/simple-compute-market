# Design: extract the change workflow repository

Status: design phase. Not planned. This design waits on the designs of the
changes that draw the workflow's boundary inside this repository, so it records
direction and questions only. The direction under "Starting direction" came from
the owner's discussion that opened the lesser goal. Everything under "Open
questions" is undecided.

## Context

- **What is on the workflow's side today.**
  - The engine: `scripts/change_workflow/` and the standalone scripts beside it.
  - The ten `change-*` skills.
  - `.agents/change-outcome.schema.json`.
  - The `change-workflow` specification and its architecture companion.
  - `docs/agents/change-workflow.md`.
  - The workflow's tests in `scripts/tests/`.

  `specify-change-workflow-and-engine` produces the authoritative list.
- **How skills load today.** They load from the repository: relative symlinks in
  `.claude/skills/` and `.codex/skills/` point at `.agents/skills/`, and
  `scripts/check_agent_skills.py` enforces one source per skill.
- **Records live outside the tree.** A change's records are untracked.
  `scripts/find_change.py` looks for them in the current checkout, then in the
  owner's workspace, which a clone names through its `workspace` remote. Record
  conversion (`scripts/change_workflow/convert.py`) migrates older records to the
  workflow log's format.
- **The OpenSpec skills** (`openspec-*`) are generated by the OpenSpec tool and
  maintained with it. They are not the workflow's.

## Starting direction

- **The workflow repository is public.** That lets a public adopter, such as this
  repository, name it and cite it. The engineering guidance is a separate matter
  and may live elsewhere.
- **Skills install into the user's harness skill directories,** shared between
  repositories. This avoids namespacing and per-repository copies. Codex has an
  equivalent directory under the user's home.
- **Each repository declares a version range, not a pin.** Python's version
  specifiers are the model.
- **Lenient versioning before a major release.**
- **Repositories call the engine only as a command,** so adopters may be written
  in any language.
- **The boundary is drawn here first.** Nothing is extracted until the changes
  that draw it have landed.

## Open questions

- **Names and licence.** The repository's name, the distribution's name, and the
  open-source licence it is published under.
- **Distribution channel.** A package index, or installation from the
  repository's tags. Shipping the skills inside the engine's distribution, with
  an install subcommand, would make one artifact carry one version for both, and
  rule out skew between the skills and the engine.
- **Several repositories on one machine.** One installed version must satisfy
  every repository's range. When it cannot, the engine refuses and names the
  conflict. Whether versions should also install side by side, with the engine
  choosing per repository, is open. Harness skill directories hold one skill per
  name, which makes side-by-side installation harder.
- **What exactly moves.**
  - The repository-independent checks: change index, tasks, change structure,
    citations.
  - The capability defaults.
  - Clones, round views, and history, whose conventions about the owner's
    workspace may need to become configuration.
- **History.** Which paths' history is carried, and how. Records and archived
  changes in this repository cite commits and paths of this repository. They stay
  valid here, but the moved files' history must still make sense on its own.
- **The cutover.** Whether to move in one change or in stages. A staged move would
  have this repository first consume the workflow from its own tree as an
  installed package, then switch to the external repository. How in-flight
  changes in this repository cross the cutover.
- **The workflow repository's own workflow.** Whether it uses itself, with its own
  OpenSpec tree, configuration, and changes, and how it validates a release
  against an adopting repository before publishing.
- **What remains in this repository's make targets.** Thin shims keep `make
  design CHANGE=…` working for the owner's habits, at the cost of a second entry
  point to keep current.
- **The lesser goal after extraction.** The goal's remaining gaps — harness
  adapters, the gateway, the hosted runner — belong to the workflow's repository
  once it exists. Whether this repository's index keeps a pointer, or the goal
  closes here with its remaining work transferred, is open.
