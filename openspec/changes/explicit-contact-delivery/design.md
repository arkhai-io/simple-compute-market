# Design

## Authority and compatibility

A profile optionally advertises the exact `contact-delivery.v1` policy. Omitting
it retains the existing serialized profile, canonical option identity and start
behavior. A policy-bearing accepted introduction refuses the ordinary start;
only the reviewed, explicitly consented finalization captures contacts.

The native `settlement` envelope and its native content address are generated by
the current contact option builder. There is no option translator. Listing IDs,
resource facts and `pricing.asking_rate` remain owned by existing publication.
A nonbinding ask adds no settlement rate, amount, funding or physical commitment.
This milestone uses policy-only packages; it does not add the separate
`accepted-listing.v1` declaration/context capability.

Private delivery configuration lives beside its contact payload: globally for
the single-origin form, or inside each configured origin. The accepted
negotiation's durable origin selects both contact and seller-owned destination.
Credentials use the existing secret-profile mechanism, never public profiles.
The buyer supplies and reviews only its own route. Both direct and origin-specific
private delivery sections are secret settings, rejected by public chart values.
Only the bare-metal composition opts into publishing the policy; the shared
registration defaults to refusing policy-bearing publication for storefronts
without the reviewed routes, migration and worker. Existing options remain readable.

## Durable transitions

The contact kit owns review/finalization state and recipient intents, serialized
through its store's explicit SQLite write transaction. Finalization captures one
immutable contact record and at most one intent per role and policy. Delivery
intents remain awaiting completion until each real non-financial settlement
operation succeeds. Exact committed finalization retries recover the same row.
An unknown provider acceptance becomes `needs_review`; no later tick resends it.

The delivery kit owns one bounded SMTP-attempt primitive with a child owning DNS
and the socket, a real monotonic deadline, verified TLS and a final claim check
before DATA. The storefront renders each recipient's existing reveal projection
and binds that attempt to its contact-kit outbox claim. The worker is registered
on the existing held/stepped lifecycle controller; no independent timer framework
or request-triggered outbound transport is added.

Payload redaction fences pending/sending intents and clears routes. A finalization
retry against a redacted record returns the established deleted outcome, never a
new reveal. Signed start and reveal retries project the currently retained contact record,
preserving recorded failures and pending-request fences. Replay outcomes omit
counterparty contacts and review tokens; an additive storefront migration removes
those fields from historical response caches without dropping request ownership,
hashes or outcome status. A review token is returned only once. If its response
is lost, an exact retry refuses with `review_invalid`; callers use a fresh
finalization ID for a new review rather than rotating the existing token.
A transmission already accepted by an external provider cannot be
recalled. Its uncertain result remains non-replayable.

## Migration and rollback

A new migration follows every existing bare-metal migration. Baselines and prior
ledger IDs are unchanged. Upgrade preserves existing introduction and market
history. The unchanged migration engine correctly classifies the upgraded ledger
as AHEAD for an old image, so that image cannot reattach the upgraded PVC.

A disabled fallback must be built with this migration-aware reader and continue
servicing accepted finalizations, unknown outcomes and recipient intents. Disable
new admission while retaining the accepted work's contact/delivery configuration;
removing that configuration also removes the worker and cannot qualify recovery.
A pre-activation snapshot/clone is an alternative only before any new committed or
unknown outcome; restoring behind accepted work would discard its fences/receipts
and is prohibited.

For a contact-only deployment, retain contact enabled and in `Settlement.priority`,
retain the migration-aware image and existing private delivery configuration, and
omit `delivery_policy` from the current named profile. New policy-bearing selections
must match that profile's currently offered policy at both preview and final
obligation construction, even while an older signed option remains listed. The
storefront must also support explicit delivery. An option without the policy keeps
its legacy behavior and may replace the old published option. Already accepted
agreements use their persisted plans: review/finalization recovery and recipient
intents keep their original policy and unknown-send fences. Configuration/startup,
signed loopback and SQLite fixtures establish this source behavior; deployed
configuration, republishing and actual delivery still require rollout verification.

## Validation and promotion

Focused source-overlay checks use exact candidate contact/delivery/storefront
modules and the exact base payment source over a verified retained dependency
environment. They are not installed-wheel or release proof. Unit controls cover
strict carriers, privacy, drift, cancellation, concurrent finalization, restart,
recipient isolation, unknown outcomes and bounded synthetic SMTP. Real SQLite and
signed loopback HTTP checks cover native option identity, deliberate finalization,
ordinary starts, disable/reopen, unbacked introduction and the migration reader
floor.

Package versions, dependent bounds/locks, installed-wheel parity, complete
repository gates and hosted qualification remain a release prerequisite. Permanent
promotion after review belongs to `openspec/specs/contact-exchange-settlement/`,
`openspec/specs/introduction-delivery/`, and storefront deployment documentation.
No repository-wide architecture layer or roadmap goal changes. The campaign index
records this additive source milestone; closing and archiving it remains pending.
