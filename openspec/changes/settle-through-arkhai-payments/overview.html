Settle through Arkhai payments

SCM's settlement slot stops being escrow-shaped; the hosted Stripe mechanism is replaced by a charge-first payments service. Openspec change settle-through-arkhai-payments.

1 · A deal is a pipeline

Negotiate

negotiation-runtime (counter / accept / exit)
→ outputs an explicit agreement on accept
→

Settle

alkahest.v1 escrow on chain
arkhai.payments.v1 balance ledger
each reads the agreement → outputs its own evidence (escrow uid / signed receipt)
→

Provision

vms / bare_metal / apicredits
discriminates on which settle kit ran, translates its evidence into its own internal "paid" form
contact-exchange.v1 fuses settle + provision: "whatever happens after negotiate, understanding its output"

Each stage understands only its predecessor's output. No shared adapter API between mechanisms. The listing advertises which kit fills each slot, so buyers and registries can filter; behavior is dispatch on the mechanism id. Core defines only what ≥ 2 of buyer, seller, registry read.

3 · arkhai.payments.v1 (stateless, no daemon)

Flow

  1. Buyer and seller each derive the same mandate from the agreement: one once part, held for term + dispute window, deal = sha256(JCS(agreement)).
  2. Buyer agent approves it (WorkOS user API key) → service-signed receipt. Tx id = mandate hash, so retries converge.
  3. Seller verifies receipt against its derived mandate → provisions.
  4. Failure while held → seller sends reverse, buyer is refunded. Otherwise the hold releases on its own.

Why charge-first

  • Fiat undoes payments by refund/dispute; it doesn't escrow. Escrow-max-then-refund was the old friction.
  • A hold is a challenge window: reversible until release, final after.
  • Cash (Stripe top-up / payout) is invisible to SCM, which trusts the ledger.
  • v1: fixed-interval deals. Spot / on-demand rates come in the service's next release.
