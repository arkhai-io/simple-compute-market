## Context

A change is worked today in a browser chat session opened with a zipped snapshot
(`make code-snapshot`) and a session prompt from `docs/prompts/`. Reviews come
from a second agent in another browser session, which receives snapshots and diffs
and whose answers are pasted back unedited. Before every implementation review the
owner runs, by hand, `make lock`, `make check-packaging`, `make test`,
`make run-e2e`, and `make fetch-e2e-logs`, and sometimes builds images and runs the
end-to-end suite against the Helm charts.

Both agent harnesses in use — Claude Code and Codex — are installed locally, run
inside the repository, and load repository skills from `.claude/skills/` and
`.codex/skills/` respectively, in the same `SKILL.md` format. The OpenSpec skills
are already committed to both, as identical copies. The Stripe skills under
`.claude/skills/` are committed as symlinks into `.agents/skills/`, which does not
exist in the repository, so those links currently resolve to nothing.

The review prompt in use covers four review kinds, asked in sequence within one
reviewer session:

- **Design review** — summarize the purpose, scope, and design; is the change
  consistent with the current codebase; what would you change about this design.
- **Implementation review** — what would you have done differently; is the
  validation strategy sound, stating the level each coverage claim actually
  operates at, and whether integration tests exercise the real typed client; does
  the documentation comply with the guidance, checked against files rather than
  task notes; is the code placed in the layers `ARCHITECTURE.md` defines.
- **Pre-closeout review** — did the implementation materially address all earlier
  feedback; what scope crept in, reviewed under the implementation questions; is
  the change ready for promotion and closeout.
- **Closeout review** — does the change comply with the documentation guidance; is
  it ready for archival.

## Goals / Non-Goals

**Goals.** The owner stops carrying text between agents, stops resuming stalled
sessions, and stops running the pre-review validation sequence by hand, while still
reading every finding and deciding every design question. Each phase's procedure is
written once, loadable by either harness. The owner's interventions are captured as
data for periodic guidance refinement.

**Non-Goals.** See the proposal: no orchestrating skill, no removal of human gates,
no per-lens reviewer agents, no third-party providers, no retirement of the browser
process yet.

## Decisions

### Leaf skills first; orchestration is a later change

Each phase gets its own skill, invoked directly by the owner and proven on a real
change before anything depends on it. An orchestrating skill that infers a change's
phase, advances it, and surveys every change in priority order is the intended end
state, and is expected to invoke the leaf skills as subagents. Designing it before
the leaves exist would fix its interfaces against guesses about where the leaves
fail. It is a separate change, opened once the leaf skills have each run on a pilot.

### One skill source, linked into each harness

A skill's single source lives in `.agents/skills/<name>/`. `.claude/skills/<name>`
and `.codex/skills/<name>` are relative symlinks to it. Two committed copies drift
— the folder `docs/prompts/` was itself created after the tombstone rule drifted
between copies — and the Stripe skills already use this layout, so it extends an
existing convention instead of adding a second one. A `make` check fails when a
skill exists for one harness and not the other, when a link does not resolve, or
when a harness directory holds a real copy of a skill that has a shared source.

This also repairs the Stripe links, whose target directory was never committed:
either their source is committed under `.agents/skills/` or the links are removed.
The OpenSpec skills are generated by the OpenSpec tooling into both harness
directories; whether to move them behind links depends on whether regeneration
would overwrite the links, and is decided when that is tested.

### Reviews are exchanged as files, not as a continued session

The reviewer harness writes each review into the change's `reviews/` directory. A
later review reads earlier reviews and their triage from that directory instead of
relying on the reviewer's session memory. That is what lets a pre-closeout review
ask "did the implementation address all your feedback" of a different session,
survive context compaction, run under either harness, and later be split across
per-lens reviewer agents that never shared a session. Continuing a reviewer session
where the harness supports it is an optimization, never a dependency.

```text
openspec/changes/<change>/reviews/        (untracked)
  01-design.md                review, prose
  01-design.findings.json     the same findings, structured
  01-design.triage.md         implementing agent's positions + owner dispositions
  02-validation.md            pre-review validation report
  03-implementation.md
  03-implementation.findings.json
  03-implementation.triage.md
  ...
```

Files are numbered in the order they were produced, so the directory reads as the
change's review history. Closeout promotes whatever is durable through the ordinary
promotion path; archival deletes the directory.

### A finding has a lens, a basis, and a severity

Classifying findings into one flat list conflates two independent questions — what
kind of attention a finding needs, and what it rests on. Test coverage is both a
kind of attention and an application of written guidance (`TESTING.md`), so a flat
`coverage` class and a flat `compliance` class overlap. A finding therefore carries
both axes:

| Lens (which review question produced it) | |
|---|---|
| `direction` | The reviewer would design or implement it differently |
| `consistency` | The change disagrees with the current codebase or with itself |
| `testing` | Validation strategy, test level, coverage |
| `documentation` | Placement, currency, citations, comment hygiene |
| `architecture` | Layering, dependency direction, ownership |
| `scope` | Work outside the change's stated boundary |
| `readiness` | Whether the change may enter its next phase |

| Basis (what the finding rests on) | |
|---|---|
| `specification` | A requirement in `openspec/specs/` or the change's own delta, cited |
| `guidance` | A written rule in `AGENTS.md`, `docs/development/`, or `openspec/README.md`, cited by heading |
| `evidence` | A claim in the change contradicted by the files themselves |
| `judgement` | The reviewer's view, resting on no written rule |

Severity is `blocking`, `should`, or `minor`.

The basis is what makes the intervention ledger useful. A `guidance` finding that
reached a review means a written rule was not mechanically enforced: the question
is which check should have caught it. A `judgement` finding the owner accepts is an
unwritten rule: the question is whether it should be written. The `direction` lens
with a `judgement` basis is where the owner's design input concentrates.

### Review kinds keep the owner's questions; the direction lens is a design discussion

The change-review skill takes the review kind as its argument and asks the
questions listed under Context, each tagged with the lens it serves. The
implementation review's "what would you have done differently" is a design question
asked late, and is prompted the way design discussion is: summarize the problem in
the reviewer's own terms, name alternatives with their trade-offs, and recommend.
The compliance lenses are prompted for exhaustive, cited checking instead.

Every review kind is run by one reviewer session covering every lens. Per-lens
reviewer agents need only a different invocation of the same skill with a lens
filter, because the finding record already names its lens.

### Triage states a position on every finding and filters none

The implementing agent reads each finding, checks it against the files, and records
its own position — agree, disagree, or partly — with evidence and a proposed
action. Agreement needs a stated reason, the same as disagreement, so that
deference to the reviewer is visible rather than the default. Every finding is
presented to the owner, ordered by lens with `direction` first, then by severity.
Nothing is applied until the owner has recorded a disposition.

On each disposition, one line is appended to a local, untracked ledger outside the
change directory, so it survives archival: the change, review kind, lens, basis,
severity, the agent's position, the owner's disposition, and a one-line summary.
The ledger is the input to the owner's periodic guidance reviews.

### Design discussion is written for depth, and preloads context

The same model has been observed to give a richer design discussion in a browser
session opened with a full snapshot than in an agent harness that loads files on
demand. Two causes are plausible: the harness's own instructions favour brevity and
action, and on-demand loading means early answers rest on a partial picture. The
design skill counters both. It reads the required guidance documents, the whole
change directory, the specification and architecture companion of every capability
the change names, and the code the design cites, before it says anything. It then
asks for a discussion, not an action: numbered open questions, each with the
options considered, their trade-offs, and a recommendation, and it edits no file
until the owner says the design is settled.

### Validation before review is a make target plus a reporting step

The local half of the sequence — `make lock`, `make check-packaging`, `make test` —
becomes one target that stops at the first failure and writes a summary. The
remote half triggers the end-to-end workflow and fetches its logs. The validation
skill runs both, reads the end-to-end logs for the failing scenario rather than
only the exit status, and writes `reviews/NN-validation.md`, which the reviewer
reads as evidence. A failure stops the review: there is no point reviewing an
implementation whose own checks have not passed, unless the owner asks for one.

### The index has a status vocabulary and a campaign priority

The orchestrator this change prepares for has to decide what may start next from
`openspec/changes/README.md`, and most status cells today are sentences. Every
change row gets a `Status` column holding exactly one of:

| Status | Meaning |
|---|---|
| `proposed` | Design not settled; no implementation plan |
| `active` | Planned; implementation may begin |
| `implementing` | Implementation under way |
| `blocked` | Must not proceed; the notes name what it waits on |
| `deferred` | No plan until a recorded activation condition is met |
| `complete` | Implemented and closed out; awaiting archival |
| `archived` | Archived; row kept while the campaign references it |

The sentence moves to a `Notes` column. Priority is a single ordered list of
campaigns at the top of the index — roadmap goals, lesser goals, and the
independent changes as one entry. Within a campaign, order comes from its
dependency graph. Priority is not assigned per change, and it lives in the index
rather than in `ROADMAP.md`, whose requirement forbids delivery sequencing.

### Browser delivery rules leave the shared guidance

`AGENTS.md` loses its "Generated implementation artifacts" section and its
references to returning a fileset; `openspec/README.md` loses its tombstone
checklist item. The same rules already live in the browser session prompts that
need them. The prohibition on a tombstone remaining in tracked files stays
enforced by `make check-comment-hygiene`. No skill names `docs/prompts/`.

## Risks / Trade-offs

- **The reviewer stops seeing what the owner saw.** A browser reviewer was given a
  snapshot and a diff by hand; a harness reviewer chooses what to read. The review
  skill names the diff command and the documents to read before answering, and the
  pilot compares its findings with what the browser process produced.
- **Running the end-to-end workflow requires a pushed branch.** Pushing is visible
  outside the machine. See Open Questions.
- **The ledger is local.** It is lost with the working copy, and is not shared
  across machines. Accepted: it is the owner's working data, and a public
  repository is the wrong home for it.
- **Symlinked skills on platforms without symlinks.** Accepted: every current
  contributor platform supports them, and the Stripe skills already depend on them.

## Open Questions

- **Authority to push.** Should the validation skill push the branch to run the
  end-to-end workflow, or stop and ask each time?
- **Helm end-to-end.** Which command builds images and runs the end-to-end suite
  against the Helm charts, and when is it owed rather than optional?
- **End-to-end run correlation.** `make run-e2e` does not report the run it
  started; confirm how `make fetch-e2e-logs` selects the run when several are in
  flight on different branches.
- **Ledger location.** Proposed: `.scm-local/agent-workflow/interventions.jsonl`,
  in the existing untracked scratch directory.
- **Mapping existing index statuses.** Rows such as "design-gated" and "local work
  complete, qualification externally blocked" need a decided mapping; proposed
  `proposed` and `blocked` respectively, with the detail in `Notes`.

## Pilot

`capacity-shape-envelope` (Goal 2) is the pilot: it has a design with open
questions and an unstarted plan of 24 tasks, so it exercises design discussion,
design review, triage, planning, implementation slices, validation, and the later
review kinds. It is off Goal 7's critical path, which continues through the browser
process meanwhile.
