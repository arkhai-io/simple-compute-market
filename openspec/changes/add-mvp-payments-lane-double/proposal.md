# Proposal

## Why

No end-to-end lane can run a purchase settled in `arkhai.payments.v1`. With no
payments target configured, every payment scenario reports a blocked skip
(`e2e-tests/tests/e2e/roles/helpers/payments.py`), so the payment path is verified only
against an external deployment. The kit's `FakePaymentsClient` is in-process: it cannot
serve a buyer CLI subprocess or a storefront container. Storefront readiness never
contacts the payments service, so nothing checks that a deployed storefront can reach it.

The payments service lives outside this repository, so it has no mock mode the way
provisioning does. Its locally verifiable stand-in has to be a double of its public HTTP
contract that runs in the lane. `add-arkhai-payments-lane-double` designs a mediation
double, rate-part qualification, contract modes, fault controls and evidence classes for
Goal 8. That scope is gated on contract publication, and none of it is needed for a
once-only purchase.

`qualify-real-provisioning-by-scenario` needs a locally verifiable buyer purchase in the
VM and bare-metal lanes, which its external-topology scenarios then extend, and a
deployment shape for the payments interface its external round can rehearse. This change
delivers both first, as the minimum `add-arkhai-payments-lane-double` later builds on.

Wiring the lanes for payments also exposed how lane configuration travels today: root
`Makefile` targets print `VAR=value` lines into generated environment files, so no lane's
configuration can be read in a file, against `DEPLOYMENT_AND_CONFIG.md`'s profile rule.
And a payments key named by an environment variable, or a CA trusted through
`SSL_CERT_FILE`, would give secrets and trust a channel beside the secret profile a
cluster already writes. This change moves both onto committed files.

## What Changes

- **R1. A payments HTTP double mirroring the service's API** (`tools/payments-lane-double`).
  It wraps the payments kit's clock-injected `PaymentsAuthority` engine, the engine
  `FakePaymentsClient` uses, so there is no second ledger. It mirrors the service's routes,
  authentication, admission, read authorization, idempotency and error codes, and serves
  whatever its engine serves; its suite and documentation claim only the once-only
  surface (approval, Agreement attachment, signed receipts, transaction snapshots, seller
  reverse, the balance read). It always signs `livemode: false`.
- **R2. A committed development CA and leaf**, deterministic and regenerated by a check,
  for the double's service name `payments-double`. Lane callers trust the CA through their
  payments configuration's `ca_bundle_path`. Production transport checks are unchanged:
  HTTPS outside loopback, no verification bypass.
- **R3. Deterministic fixture accounts.** Buyer and seller accounts, bearer tokens and the
  receipt-signing key are visibly public development values, never to be used on a public
  network. The double seeds the buyer's balance; funding is otherwise topology.
- **R4. Lane wiring in the VM, bare-metal and API-credit lanes.** Each lane runs the double
  and configures its storefront for payments, and its runner reads a shared payments
  profile and a profile of the lane's own. The bare-metal and API-credit payment scenarios
  run rather than skip, as do the VM payment scenario's once-only stages; its case stages
  report a blocked skip naming a missing mediation target. A lane-owned target that is not
  ready fails lane setup by name.
- **R5. A pinned dispute authority nobody can answer.** The lane registries recommend a
  fixture authority whose origin is under `.invalid`, whose record key has no usable
  private half, and whose account has no bearer token at the double.
- **R6. The payer's balance read.** `PaymentsClient.get_balance(account)` calls the
  service's `GET /balances/{account}`; the engine gains the balance view the double and
  `FakePaymentsClient` serve.
- **R7. The harness readiness probe trusts a configured CA**, `PAYMENTS.CA_BUNDLE_PATH`,
  keeping environment proxies disabled.
- **R8. Storefront chart payments options.** Both storefront charts gain a CA bundle option
  (ConfigMap key first, Secret key second, no default) that mounts the bundle and derives
  `[Settlement.arkhai_payments].ca_bundle_path`. The payments key travels in the agent's
  runtime secret overlay; no chart option or variable carries it.
- **R9. The local Helm release rehearses a deployment's payments interface.** A
  `payments-lane-double` subchart, enabled only by the local deploy target, and payments
  configured through the values a deployment supplies, never `development_auth`.
- **R10. A rerunnable storefront payments check.** The three storefront CLIs gain
  `check-payments --account`, an authenticated balance read from the storefront's own
  configuration and container, run by lane setup, by a `helm test` pod, and by a
  deployment.
- **R11. Lane and stack configuration in committed files.** Every lane and the full local
  stack take their configuration from committed Compose overlays, profiles and secret
  overlays: development binds move from the base and domain Compose files, which lose
  their required-variable guards, into the root-level overlays; the provisioning services
  take committed site profiles; the root `Makefile`'s `e2e-*-dev-env`,
  `e2e-*-stack-env`, `e2e-dev-identities(-env)` and `e2e-<lane>-payments-env` targets are
  retired; the provisioning mode is the one value a run supplies. Tests hold every
  restated value to its source.
- **R12. The registry takes profile-shaped env files.** `core/registry` loads
  `config-<profile>.env` from `CONFIG_DIRECTORY` under `ACTIVE_PROFILES`, carries its filter
  specification path as a setting, and drops five variables nothing reads. All five lane
  registries use it. The registry chart renders its values as an env-file profile and
  takes secret settings as a `secretProfile` from an existing Secret, retiring
  `auth.bootstrapKeySecret` and `auth.adminKeySecret`.
- **R13. Secrets through secret overlays; trust through configuration.** The payments kit
  gains `api_key` (secret) and `ca_bundle_path`, with one key resolution and a CA argument
  on `PaymentsClient`; dispute credentials gain `api_key`, and `MediationCredential`
  carries the resolved token. Storefronts' payments, dispute and wallet keys live in their
  secret overlays; the buyer keeps its named-variable provider.

First consumers:
- `qualify-real-provisioning-by-scenario`'s locally verifiable buyer purchases in the VM
  and bare-metal lanes, and its external round's first check of a topology;
- the existing bare-metal and API-credit payment scenarios and the VM payment scenario's
  once-only stages, which stop skipping.

No mediation double, contract mode selector, fault control, evidence class or production
guard on fixture identities is introduced; those remain `add-arkhai-payments-lane-double`'s.
Payment scenarios are not served on the local Helm release. The registry does not move
onto Dynaconf here, and the signing credential's delivery is unchanged.

## Capabilities

### New Capabilities

None. The double is a test collaborator, not a production authority.

### Modified Capabilities

- `test-compatibility`: lanes run payment scenarios against an in-lane payments double;
  lane-owned targets fail rather than skip when unready; a lane's runner reads committed
  lane profiles.
- `deployment-state`: the storefront charts' CA option, the local release's payments
  rehearsal, the storefront payments check, a storefront's secrets in its secret overlay,
  stack configuration in committed files, and the registry's profile env files and chart.
- `market-composition`: the payments kit reads an account's own balance.
- `settlement-configuration`: the payments key and dispute credentials may be secrets in
  configuration, and the payments CA bundle is configured.

## Impact

- New `tools/payments-lane-double` project, image, TLS and account fixtures; a new kind of
  tool in `tools/README.md`.
- `kit/arkhai-payments`: `PaymentsAuthority.balance`, `PaymentsClient.get_balance` and its
  CA argument, `FakePaymentsClient.get_balance`, `api_key`, `ca_bundle_path`, key
  resolution, the payments check function, and their tests.
- `kit/deal-lifecycle` and `kit/arkhai-mediation`: `DisputeCredential.api_key`,
  `MediationCredential` carrying the token; their callers in the VM and bare-metal
  storefronts and buyers.
- `domains/vms/storefront`, `domains/bare_metal/storefront`, `domains/apicredits/storefront`:
  the `check-payments` subcommand.
- `core/registry`: profile env files, the filter specification setting; its Dockerfile and
  `.env.docker-compose`.
- `e2e-tests`: lane runner profiles, the payments helper's `LANE_OWNED` rule, configured CA
  and token handling, the VM payment scenario's mediation prerequisite and own resource.
- Compose: the base and domain files, the `-local` and `-lane` overlays, the full local
  stack, `dev-env/registry/`, `dev-env/provisioning/`, the storefronts' secret overlays;
  the wallet env files deleted.
- Root and `e2e-tests` Makefiles: the image build, the lane targets naming only their
  files and mode, the environment targets retired.
- `helm`: the `payments-lane-double` subchart, the storefront and bare-metal storefront
  charts' CA option and render tests, the registry chart's env-file profile and
  `secretProfile`, the local release values and deploy target, `topology-secrets.sh`.
- `add-arkhai-payments-lane-double`: its D1 and D7 are revised at its design
  reverification to extend this double, add mediation as a sibling project, and own the
  production guard; it inherits the mediation credential change.
- `qualify-real-provisioning-by-scenario`: its storefront chart CA option is delivered
  here, as a configured `ca_bundle_path`.
- Operators: a registry chart values file using `auth.*KeySecret` is refused at render and
  moves to `secretProfile`.
- No database migration.
